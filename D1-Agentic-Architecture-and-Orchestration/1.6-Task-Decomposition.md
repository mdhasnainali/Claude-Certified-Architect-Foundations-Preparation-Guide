# 1.6 Task Decomposition

## Goal
After this you can choose between a fixed prompt chain and dynamic decomposition, and split a big review so attention doesn't spread thin. *(Task statement 1.6)*

## Guess first
1. A pull request changes 14 files. One review pass flags a pattern as a bug in one file and approves the same code in another file. Will a model with a bigger context window fix this?
2. "Add comprehensive tests to this legacy codebase." Can you write the full step list before you start?

## Idea
Two ways to break a big task into steps:

| | Fixed pipeline (prompt chaining) | Dynamic, adaptive decomposition |
|---|---|---|
| Plan made | Before the start, by you | During the work, from what is found |
| Fits | Predictable work with known aspects: code review checklists, extract → validate → format | Open-ended investigation: debugging, legacy test coverage, research |
| Strength | Predictable, testable, cheap | Handles surprises |
| Weakness | Can't adapt to findings | Less predictable, costs more |

**Prompt chaining:** each step is one focused LLM call; its output feeds the next step. For a big code review the classic chain is:
1. **Per-file passes** — each file alone, local bugs only.
2. **One integration pass** — only cross-file problems: data passed between files, mismatched function contracts, duplicated logic.

Why split? **Attention dilution.** With many files in one prompt, depth becomes uneven: detailed comments for some files, shallow ones for others, missed bugs, even contradictions. A bigger context window gives more *room*, not better *attention* (official sample question 12).

**Dynamic decomposition:** the next subtask depends on what the last step found. Example — "add comprehensive tests to a legacy codebase":
1. **Map the structure** first (Glob for modules and existing tests, Grep for entry points).
2. **Find high-impact areas** (money paths, often-changed files, code with no tests).
3. **Make a prioritised plan.**
4. **Adapt the plan** as you discover hidden dependencies.

This is the orchestrator-workers idea from [1.2 Coordinator and Subagents](1.2-Coordinator-and-Subagents.md): subtasks can't be known in advance.

*In Python terms:* a fixed chain is a function pipeline — `fmt(validate(extract(doc)))`. Dynamic decomposition is a work queue where handling one item can push new items onto the queue (like BFS).

Anthropic's "Building effective agents" names the workflow patterns: **prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer**. Start with the simplest one that works.

## Code

**File:** [`codes/1_6_decomposition.py`](codes/1_6_decomposition.py) · run `make run 1_6_decomposition`

Python 3.13+, `anthropic` 2.13. Needs `ANTHROPIC_API_KEY`. Cost grows with file count.
Save as `1_6_decomposition.py`, run `uv run --with anthropic python 1_6_decomposition.py a.py b.py c.py` on 3+ files of one of your projects.

```python
# 1_6_decomposition.py — anthropic 2.14. Run: make run 1_6  (reviews extra/*.py)  or pass files: ... 1_6_decomposition.py a.py b.py
"""Prompt chaining: one big review split into small, focused calls.

Single pass = ONE call: all files + "find every bug". Attention spreads thin, so bugs get missed.
Chain = Step 1: one call PER FILE (local bugs) → Step 2: one call with ALL files (cross-file bugs only).

Analogy: inspecting a house. Single pass = one quick walk-through, looking at everything at once.
Chain = inspect each room alone (Step 1), then check only the pipes and wires BETWEEN rooms (Step 2).
Python view: Step 1 = unit tests, Step 2 = integration test.
"""

import pathlib
import sys

import anthropic

client = anthropic.Anthropic()

def ask_claude(prompt: str) -> str:
    """One API call: prompt in, text out. Every step of the chain uses this."""
    response = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=4000,
        messages=[{"role": "user", "content": prompt}],
    )
    return "".join(block.text for block in response.content if block.type == "text")

EXTRA_DIR = pathlib.Path(__file__).parent / "extra"
paths = [pathlib.Path(arg) for arg in sys.argv[1:]] or sorted(EXTRA_DIR.glob("*.py"))
# {"orders.py": "<source code>", ...}
sources = {path.name: path.read_text() for path in paths}

# Step 1 — N calls, one per file. The model sees ONE small file, so it reads it closely.
# Weak spot: it can't see the other files, so it can't catch bugs BETWEEN files.
per_file_reviews = {
    name: ask_claude(
        "Review ONLY this file for bugs. Max 5 findings: line, issue, fix.\n"
        + f"<file name='{name}'>\n{source}\n</file>"
    )
    for name, source in sources.items()
}
for name, review in per_file_reviews.items():
    print(f"=== {name}\n{review}\n")

# Step 2 — 1 call with ALL files. Told to skip local bugs (Step 1 did them),
# so its whole attention goes to the seams: what one file passes to another.
# It gets the raw files again, NOT Step 1's answers.
all_files = "\n".join(
    f"<file name='{name}'>\n{source}\n</file>" for name, source in sources.items()
)
print(
    "=== CROSS-FILE\n"
    + ask_claude(
        "These files were already reviewed one by one. Report ONLY cross-file problems: "
        + "data passed between files, mismatched function contracts, duplicated logic.\n"
        + all_files
    )
)
```

Expected output (findings depend on your code):
```
=== a.py
1. Line 42 — `user_id` can be None; `.lower()` raises. Fix: guard or default.
...
=== CROSS-FILE
1. b.py calls `load(path, strict)` but a.py defines `load(path)` — the second argument fails.
```

**Predict first, then change and run:** add a third step: send all files in one prompt, "Review these files for bugs." Use 8+ files. Compare it with the chained output. What differs?

<details><summary>Answer</summary>

The single pass usually gives fewer findings per file, uneven depth (later files get shallow comments), and sometimes contradictions. The chain gives even depth per file, and the cross-file pass catches contract mismatches that per-file passes can't see.

</details>

## When to use · gotchas
- **Fixed chain** for repeatable checklists; **dynamic** for open questions. Don't use dynamic decomposition for a fixed checklist (wastes tokens, less predictable). Don't force a fixed chain on open-ended work (it misses what it discovers).
- Per-file passes are independent → run them **in parallel** to save time.
- The integration pass needs a **narrow instruction** ("cross-file only"), or it repeats the local findings.
- **Exam distractors for big reviews:** "use a bigger model / bigger context window" (attention, not room, is the issue), "run 3 passes and keep issues found twice" (hides real bugs that show up only sometimes), "make developers split their PRs" (moves the burden, doesn't fix the system).

## Quiz
**1.** A nightly review of 20-file changesets gives detailed comments on the first files and shallow ones on the last files. Best fix? A) Bigger context window · B) Per-file passes plus one cross-file integration pass · C) Three full passes, keep issues found twice · D) Limit PRs to 5 files

<details><summary>Answer</summary>

**B.** It fixes the root cause: attention dilution. A misreads the problem; C suppresses real but intermittent findings; D moves the burden to developers.

</details>

**2.** Invoice processing: extract fields → check totals → map to the ERP format. Same steps every time. Which pattern?

<details><summary>Answer</summary>

A fixed prompt chain. The steps are known and repeatable.

</details>

**3.** "Find out why checkout latency doubled since last week." Which pattern, and why?

<details><summary>Answer</summary>

Dynamic decomposition. Each next step depends on what the last one found (logs → a slow query → a recent migration ...).

</details>

**4.** Why doesn't a 1M-token context window fix the 14-file review?

<details><summary>Answer</summary>

The problem is attention quality, not capacity. Many files in one pass spread the model's focus, so depth becomes uneven and findings contradict.

</details>

**5.** What is the right first step for "add comprehensive tests to a legacy codebase"?

<details><summary>Answer</summary>

Map the structure (Glob/Grep), find the high-impact areas, then build a prioritised plan that adapts as dependencies appear — not "write tests file by file from the top".

</details>
