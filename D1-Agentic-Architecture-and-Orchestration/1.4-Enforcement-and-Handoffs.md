# 1.4 Enforcement and Handoffs

## Goal
After this you can tell when a rule must live in code instead of the prompt, build a prerequisite gate, and write a handoff a human can act on at once. *(Task statement 1.4)*

## Guess first
1. Your system prompt says "ALWAYS verify the customer before a refund." It works in 99% of chats. Good enough for refunds?
2. A human takes over an escalated chat but can't see the transcript. Which facts do they need first?

## Idea
There are two ways to control the order of steps:

| | Prompt-based guidance | Programmatic enforcement |
|---|---|---|
| How | Instructions, few-shot examples | Hooks, prerequisite gates, checks inside the tool |
| Guarantee | Probabilistic — a non-zero failure rate | Deterministic — every time |
| Use for | Tone, format, soft preferences | Identity checks, money, legal and safety rules |

**Rule:** if one mistake costs money, breaks a law or a policy, or hurts trust → enforce it in code. Writing "MUST" or "CRITICAL", or adding few-shot examples, makes failure rarer — never impossible. (This is official sample question 1: options B and C rely on the prompt and are wrong.)

**Prerequisite gate.** Block a downstream tool until an upstream step is done. Example: block `lookup_order` and `process_refund` until `get_customer` has **returned** a verified customer ID. You need two parts:
- after `get_customer` runs → remember the verified ID (session state);
- before a guarded tool runs → check that state; if missing, **deny** with a reason that says what to do next.

Claude receives the denial as the tool result. A reason like "Call get_customer first" lets it recover by itself.

*In Python terms:* a gate is like a FastAPI dependency or a `@login_required` decorator: the check runs on every request, whatever the caller intended. A prompt rule is like a comment saying "please log in first".

**Multi-concern requests.** "My order is late, I was charged twice, and I want to change my email." Split it into separate items. Investigate each one — in parallel where you can — using the shared context (same customer ID). Then send **one** combined answer.

**Structured handoff.** When the agent escalates, the human has no transcript. Give them a compact, self-contained summary:

```json
{
  "customer_id": "C-1042",
  "verified": true,
  "issue": "Charged twice for ORD-9 ($650.00 on 2026-11-20 at 10:02 and 10:03)",
  "root_cause": "Payment retry after a gateway timeout created a second charge",
  "done_so_far": ["Confirmed both charges in billing", "Refund blocked: over the $500 agent limit"],
  "refund_amount": 650.00,
  "recommended_action": "Approve a refund of the second charge only",
  "customer_wants": "Refund to the original card and an email confirmation"
}
```
Exact IDs, amounts and dates. No "about $600", no "see chat".

```python
# 1_4_enforcement_and_handoffs.py — Python 3.13+. Runs offline: python3 1_4_enforcement_and_handoffs.py (same callback shape the Agent SDK calls)
import asyncio

verified: set[str] = set()  # customer IDs that get_customer has verified this session

async def remember_verified(inp, tool_use_id, ctx):  # PostToolUse, matcher: get_customer
    if inp["tool_response"].get("verified"):
        verified.add(inp["tool_input"]["customer_id"])
    return {}

async def require_verified(inp, tool_use_id, ctx):   # PreToolUse, matcher: lookup_order|process_refund
    cid = inp["tool_input"].get("customer_id")
    if cid in verified:
        return {}  # no decision → normal permission flow
    return {"hookSpecificOutput": {
        "hookEventName": "PreToolUse",
        "permissionDecision": "deny",
        "permissionDecisionReason": f"Customer {cid} is not verified. Call get_customer first."}}

async def demo():
    refund = {"tool_name": "mcp__support__process_refund",
              "tool_input": {"customer_id": "C7", "amount": 40}}
    print("before:", await require_verified(refund, None, None))
    await remember_verified({"tool_name": "mcp__support__get_customer",
                             "tool_input": {"customer_id": "C7"},
                             "tool_response": {"verified": True}}, None, None)
    print("after: ", await require_verified(refund, None, None))

asyncio.run(demo())
```

Expected output:
```
before: {'hookSpecificOutput': {'hookEventName': 'PreToolUse', 'permissionDecision': 'deny', 'permissionDecisionReason': 'Customer C7 is not verified. Call get_customer first.'}}
after:  {}
```

Wiring it into an agent (your MCP tools are named `mcp__<server>__<tool>`):
```python
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

options = ClaudeAgentOptions(
    mcp_servers={"support": support_server},  # your get_customer, lookup_order, process_refund tools
    hooks={
        "PostToolUse": [HookMatcher(matcher="mcp__support__get_customer", hooks=[remember_verified])],
        "PreToolUse": [HookMatcher(matcher="mcp__support__lookup_order|mcp__support__process_refund",
                                   hooks=[require_verified])],
    },
)
```
The demo passes `tool_response` as a simple dict. A real MCP tool returns content blocks — print `inp["tool_response"]` once and parse it.

## When to use · gotchas
- **Gate every tool that matters,** not just one. Here both `lookup_order` and `process_refund` need the verified ID.
- **The deny reason is an instruction to Claude.** "Denied." leaves it stuck or retrying. Say the next step.
- **Don't gate soft things.** Greeting style or answer format don't need code — prompts are fine and cheaper.
- **Handoffs must stand alone.** The human can't scroll up. Exact numbers, what was done, what you recommend.
- **Hooks vs a check inside the tool:** both are programmatic. A check inside `process_refund` itself is also a valid gate. Hooks are handy when one rule spans several tools. Mechanics in [1.5 Hooks](1.5-Hooks.md).

## Try it
*≤ 10 min.* New rule: `process_refund` also needs `lookup_order` to have run for **that** `order_id` first. Extend `1_4_enforcement_and_handoffs.py`.

<details><summary>Solution</summary>

```python
looked_up: set[str] = set()

async def remember_lookup(inp, tool_use_id, ctx):    # PostToolUse, matcher: lookup_order
    looked_up.add(inp["tool_input"]["order_id"])
    return {}

async def require_lookup(inp, tool_use_id, ctx):     # PreToolUse, matcher: process_refund
    oid = inp["tool_input"].get("order_id")
    if oid in looked_up:
        return {}
    return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny",
            "permissionDecisionReason": f"Call lookup_order for {oid} before refunding it."}}
```
Register both hooks on `process_refund`. If either denies, the call is blocked (deny always wins).

</details>

## Quiz
**1.** In 8% of chats the agent issues store credit before checking the return window. The system prompt already says "check the return window first". Most effective fix? A) Write the rule in capitals at the top · B) Add 5 few-shot examples · C) Block `issue_credit` in code until `check_return_window` has returned "eligible" · D) Use a larger model

<details><summary>Answer</summary>

**C.** A policy rule needs a deterministic guarantee. A, B and D only lower the failure rate.

</details>

**2.** Human agents say escalated cases take 10 minutes to understand. They can't see the transcripts. Fix?

<details><summary>Answer</summary>

Make the agent compile a structured handoff when it escalates: customer ID, issue, root cause, amounts, what was already done, recommended action.

</details>

**3.** When is prompt-based guidance enough?

<details><summary>Answer</summary>

When a mistake is cheap and easy to fix: tone, wording, formatting, soft ordering preferences.

</details>

**4.** A customer lists three problems in one message. The agent solves the first and stops. Which pattern is missing?

<details><summary>Answer</summary>

Decompose the request into separate items, investigate each (in parallel, sharing the customer context), then write one combined answer.

</details>

**5.** Fix the bug: a gate returns `permissionDecisionReason: "Denied."` and the agent keeps retrying the same refund.

<details><summary>Answer</summary>

The reason gives Claude no way forward. Say what to do: "Customer not verified. Call get_customer with the customer's email first."

</details>
