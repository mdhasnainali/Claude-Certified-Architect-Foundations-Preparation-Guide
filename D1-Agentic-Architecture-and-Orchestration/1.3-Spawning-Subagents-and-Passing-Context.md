# 1.3 Spawning Subagents and Passing Context

## Goal
After this you can configure subagents in the Agent SDK, give them exactly the context they need, and start several in parallel. *(Task statement 1.3)*

## Guess first
1. The coordinator has read 30 pages of findings. It starts the synthesis subagent with the prompt "Write the report." What does the subagent know about the findings?
2. You want 3 searches to run at the same time. Should the coordinator start them in 3 turns or in 1 turn?

## Idea
**How a subagent starts.** The coordinator calls a tool. The exam guide calls it the **Task tool**. Today's Agent SDK calls it **`Agent`** (renamed in Claude Code v2.1.63; the `system:init` tool list still says `Task`). Same tool. The coordinator must be allowed to use it: put `"Task"` (today `"Agent"`) in `allowedTools`. In a headless app with no approval callback, a tool that isn't allowed is denied — so the coordinator can't delegate.

**AgentDefinition** describes one subagent type:

| Field         | What it does                                                                           |
| ------------- | -------------------------------------------------------------------------------------- |
| `description` | *When* to use this agent. The coordinator reads it to choose — like a tool description |
| `prompt`      | The subagent's system prompt: role, rules, output format                               |
| `tools`       | The only tools it may use (least privilege). Leave it out → it inherits all tools      |
| `model`       | Optional, e.g. `"haiku"` for cheap reading-heavy work                                  |
 
**The big rule: a subagent starts with a fresh context.** It does **not** get the coordinator's conversation, its tool results, or its system prompt. It gets its own `prompt`, the project CLAUDE.md, its tools — and **the prompt string of the Task/Agent call. That string is the only thing passed from parent to child.** There is also no shared memory between two calls of the same subagent. So put complete findings, file paths, error texts and decisions **directly in that prompt**.

**Keep content and metadata apart.** Pass findings in a structured format — for example one JSON object per claim with `source`, `date`, `page`. Free-text summaries lose the link between a claim and its source, and the final report can't cite it.

**Parallel = one response.** When the coordinator puts several Task/Agent calls in **one** response, they run at the same time. Total time ≈ the slowest one. One call per turn runs them one after another.

**Only the final message comes back.** The subagent's tool calls and reading stay inside it. The parent gets a short result, so its own context stays small.

**Fork** = a subagent or session that starts from a **copy** of the conversation so far, instead of fresh. Use it to try two different approaches from the same analysis. More in [1.7 Sessions Resume and Fork](1.7-Sessions-Resume-and-Fork.md).

*In Python terms:* a subagent is like `subprocess.run(...)`, not a thread. It shares no variables with you. Everything it needs goes in as arguments; you get back only its output.

## Code

**File:** [`codes/1_3_parsing_context.py`](codes/1_3_parsing_context.py) · run `make run 1_3_parsing_context`

Python 3.13+. No API key needed. Save as `1_3_parsing_context.py`, run `python3 1_3_parsing_context.py`.
This builds the prompt the coordinator should send to the synthesis subagent.

```python
# 1_3_parsing_context.py — Python 3.13+, no API key needed: python3 1_3_parsing_context.py
import json

subagent_findings = [  # what the search and document subagents returned
    {
        "claim": "62% of illustrators use AI tools weekly",
        "source": "https://example.org/survey-2026",
        "date": "2026-03",
        "from": "web-search",
    },
    {
        "claim": "Stock-music royalty income fell 9%",
        "source": "music-report.pdf, p.14",
        "date": "2025-11",
        "from": "doc-analysis",
    },
]

def build_synthesis_prompt(section: str, findings: list[dict]) -> str:
    numbered = [
        {"id": number, **finding} for number, finding in enumerate(findings, start=1)
    ]
    return (
        f"Write the section '{section}'.\n"
        "Use ONLY the findings below. Cite each claim as [id]. Keep dates.\n"
        "If findings disagree, show both with their sources; do not pick one.\n"
        "<findings>\n"
        + "\n".join(json.dumps(finding) for finding in numbered)
        + "\n</findings>"
    )

print(build_synthesis_prompt("Creative jobs", subagent_findings))
```

Expected output:
```
Write the section 'Creative jobs'.
Use ONLY the findings below. Cite each claim as [id]. Keep dates.
If findings disagree, show both with their sources; do not pick one.
<findings>
{"id": 1, "claim": "62% of illustrators use AI tools weekly", "source": "https://example.org/survey-2026", "date": "2026-03", "from": "web-search"}
{"id": 2, "claim": "Stock-music royalty income fell 9%", "source": "music-report.pdf, p.14", "date": "2025-11", "from": "doc-analysis"}
</findings>
```

In an Agent SDK app, Claude (the coordinator) writes this prompt itself when it calls the Agent tool. So you add the rule to the coordinator's system prompt: *"When you call the synthesizer, paste every finding as JSON with its source and date. It cannot see your conversation."* In a pipeline you control in code, you build the prompt yourself, as above.

**Predict first, then change and run:**
1. Delete the `"date"` field from both findings. What can the synthesis subagent no longer do well?
2. Add a third finding: `{"claim": "41% of illustrators use AI tools weekly", "source": "https://example.net/poll-2024", "date": "2024-05", "from": "web-search"}`. What should a good synthesis write?

<details><summary>Answers</summary>

1. It can't tell old data from new. Two numbers from different years look like a contradiction instead of a trend.
2. Both numbers, each with its source and date — for example "41% in May 2024 [3], 62% in March 2026 [1]". It must not silently pick one.

</details>

## When to use · gotchas
- **"The subagent will figure it out from context"** — no. It has no parent context. "Analyse the error we discussed" fails; paste the error.
- **Missing `Task`/`Agent` in `allowedTools`** → the coordinator does everything itself or is blocked.
- **Too many tools on a subagent** → it wanders outside its role (a synthesis agent starts doing web searches). Give each role only its tools.
- **Sequential spawning** wastes time when the subtasks are independent. Tell the coordinator: "start independent subagents in the same response".
- **The parent may re-summarise** a subagent's result. If you need it word for word in the final answer, say so in the coordinator's prompt.
- Current SDK detail (not on the exam): subagents can run in the background by default, and you can cap depth, concurrency and spend (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, `max_budget_usd`).

## Try it
*≤ 10 min.* Write an `AgentDefinition` named `doc-analyzer`. It reads PDFs and markdown files in `./docs`, must never change files, uses a cheap model, and returns findings with page numbers. Also write the `allowed_tools` list the coordinator needs.

<details><summary>Solution</summary>

```python
from claude_agent_sdk import AgentDefinition, ClaudeAgentOptions

doc_analyzer = AgentDefinition(
    description="Reads documents in ./docs and extracts findings with page numbers. "
                "Use for questions answered by internal reports, not the web.",
    prompt="Read only files in ./docs. Return a JSON list of "
           "{claim, file, page, quote}. Never guess a page number.",
    tools=["Read", "Grep", "Glob"],   # read-only: no Write, Edit, Bash
    model="haiku",
)
options = ClaudeAgentOptions(agents={"doc-analyzer": doc_analyzer},
                             allowed_tools=["Agent", "Read", "Grep", "Glob"])
```

</details>

## Quiz
**1.** The final report has claims with no sources, although the web search subagent returned URLs. The coordinator sent the synthesis agent: "Summary: the search found X, Y and Z." Best fix?

<details><summary>Answer</summary>

Pass the findings in a structured format that keeps content and metadata together (claim, URL, document, page, date) in the synthesis subagent's prompt. The free-text summary dropped the sources.

</details>

**2.** A coordinator has `allowed_tools=["Read", "Grep"]` and two subagents defined. It never delegates and does all the work itself. Fix?

<details><summary>Answer</summary>

Add the subagent tool to `allowedTools`: `"Task"` in the exam's words, `"Agent"` in today's SDK.

</details>

**3.** Four independent searches take 4× as long as one. Logs show one Task call per coordinator turn. Fix?

<details><summary>Answer</summary>

Have the coordinator emit all four Task calls in a single response so they run in parallel.

</details>

**4.** Why does a subagent fail with the prompt "Fix the bug we found earlier"?

<details><summary>Answer</summary>

Subagents don't inherit the parent's conversation. It has never seen "the bug". The prompt must contain the error message, the file paths and what was already tried.

</details>

**5.** Which `AgentDefinition` field does the coordinator use to decide which subagent to call?

<details><summary>Answer</summary>

`description`. Write it like a good tool description: what it does and when to use it.

</details>
