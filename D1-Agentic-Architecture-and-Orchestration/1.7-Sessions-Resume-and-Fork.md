# 1.7 Sessions Resume and Fork

## Goal
After this you can choose between **resume**, **fork**, and **a fresh session with a summary** — and know which one the exam wants in each case. *(Task statement 1.7)*

## Guess first
1. Yesterday Claude analysed your auth module. Today you changed two of its files. You resume yesterday's session. Does Claude know about your changes?
2. You want to compare two refactoring plans that both start from the same analysis. One session or two?

## Idea
A **session** is the saved conversation: your prompts, every tool call, every tool result, every answer. Claude Code writes it to disk (`~/.claude/projects/<folder>/<session-id>.jsonl`). It saves the **conversation, not your files**.

Three moves:

| Move                | Claude Code CLI                                                      | Agent SDK (Python)                                 | Use when                                                                        |
| ------------------- | -------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------- |
| **Resume**          | `claude --resume <name or id>` · `claude --continue` (latest here)   | `resume=session_id` · `continue_conversation=True` | Most of the earlier context is still true                                       |
| **Fork**            | `claude --resume <name> --fork-session` · `/branch` inside a session | `resume=session_id, fork_session=True`             | Try different approaches from one shared baseline; the original stays unchanged |
| **Fresh + summary** | New `claude` session, paste a structured summary                     | New `query()` with the summary in the prompt       | Old tool results are stale, or the context is bloated                           |

**Names make resuming easy:** start with `claude -n auth-audit`, or rename with `/rename auth-audit`, then come back with `claude --resume auth-audit`.

**The stale-context trap.** A resumed session still holds the **old** tool results — file contents as Claude read them yesterday. Claude is not told that files changed. So:
- **Few changes** → resume, and say exactly what changed: *"I edited `src/auth/token.py` since your analysis. Re-read only that file."* A targeted re-check beats re-exploring everything.
- **Many changes** → start fresh with a structured summary of the findings that are still valid, plus the list of changed files. Stale results make Claude confidently wrong, which is worse than starting clean.

**Fork details.** A fork gets its own session ID; the original's history is untouched. But a fork branches the *conversation*, not the *filesystem*: if a fork edits a file, the edit is real for every session in that folder.

*Git terms (your daily tool):* resume = check out a branch and keep committing. Fork = `git branch` from the current commit — but only the chat history branches, not the working tree. Fresh + summary = a new repo whose README lists the decisions so far.

## Code

**File:** [`codes/1_7_resume_and_fork.py`](codes/1_7_resume_and_fork.py) · run `make run 1_7_resume_and_fork`

**Part A — Claude Code CLI** (your normal login, no API key). Run these in any git project:

```bash
claude -n test-audit           # 1. named session: ask "Map this repo's test setup: frameworks, fixtures, slow tests."
                               #    then /exit
claude --resume test-audit     # 2. same session, full context: ask "Which 3 tests are slowest?"
claude --resume test-audit --fork-session
                               # 3. a copy: ask "Plan approach B: replace fixtures with factories."
claude --resume test-audit     # 4. the original: approach B is NOT in its history
```
Inside a session: `/rename <name>`, `/branch <name>` (fork and switch), `/resume` (picker), `/compact` (summarise to free context).

**Part B — Agent SDK.** `claude-agent-sdk` 0.2.188, needs `ANTHROPIC_API_KEY`. Run inside a project folder: `uv run --with claude-agent-sdk python 1_7_resume_and_fork.py`.

```python
# 1_7_resume_and_fork.py — claude-agent-sdk 0.2.188. Run: uv run --with claude-agent-sdk python 1_7_resume_and_fork.py
import asyncio
from claude_agent_sdk import ClaudeAgentOptions, ResultMessage, query

async def run(prompt: str, **opts) -> str:
    sid = None
    async for m in query(prompt=prompt, options=ClaudeAgentOptions(
            allowed_tools=["Read", "Grep", "Glob"], **opts)):
        if isinstance(m, ResultMessage):
            sid = m.session_id
            print(f"[{m.subtype}] session={sid}\n{m.result or ''}\n")
    return sid

async def main():
    base = await run("Map this repo's test setup: frameworks, fixtures, slow tests.")
    # Branch A and B start from the SAME analysis; base stays unchanged
    a = await run("Plan approach A: speed up tests with parallel runs.", resume=base, fork_session=True)
    b = await run("Plan approach B: speed up tests with better fixtures.", resume=base, fork_session=True)
    # Later: continue the original line of work with a targeted update
    await run("I edited tests/conftest.py since your analysis. Re-read only that file, "
              "then update your summary.", resume=base)

asyncio.run(main())
```

Expected output (text varies; the IDs are what matter):
```
[success] session=5b3f2c1a-...     ← base
[success] session=9e07d4b2-...     ← fork A: new ID
[success] session=c41a88f0-...     ← fork B: another new ID
[success] session=5b3f2c1a-...     ← resume: same ID as base
```

**Predict first, then check:** in Part A, step 3 — ask the fork to actually edit a test file. Then in step 4, ask the original "What does that test file contain now?" What happens?

<details><summary>Answer</summary>

The edit is real on disk (forks don't branch files). But the original's history still has the old file contents, so it may answer from stale memory — unless it re-reads the file. That is exactly why you tell a resumed session what changed.

</details>

## When to use · gotchas
- **Resume ≠ refresh.** Resuming does not re-read changed files. You must say what changed.
- Don't resume one session in two terminals at the same time — messages can be lost. Fork each one instead.
- `claude --resume` does not restore flags such as `--allowedTools`, `--mcp-config`, `--add-dir`. Pass them again.
- Sessions from `claude -p` and the Agent SDK don't show in the picker. Resume them by ID.
- Session files live on one machine. On another machine (CI, containers), pass a summary — or use an SDK session store.
- A subagent can be resumed too: its own transcript is kept, and you resume the parent session that started it.

## Quiz
**1.** A session is resumed after a teammate refactored 12 files. The agent now cites functions that no longer exist. Best approach? A) Keep resuming and correct it when it is wrong · B) Start a new session with a structured summary of the still-valid findings and the list of changed files · C) Fork the session · D) Raise the context window

<details><summary>Answer</summary>

**B.** Most of the old tool results are stale. A fresh session with a correct summary is more reliable. C copies the same stale history.

</details>

**2.** You want to compare two migration strategies from one 40-minute codebase analysis, without doing the analysis again. What do you use?

<details><summary>Answer</summary>

Fork the session: `--resume <name> --fork-session` (CLI) or `fork_session=True` (SDK), once per strategy. The baseline stays unchanged.

</details>

**3.** Only one file changed since yesterday's long analysis. Resume or start fresh?

<details><summary>Answer</summary>

Resume, and tell the agent exactly which file changed so it re-analyses only that file.

</details>

**4.** Agent SDK: you run `query(..., resume=base, fork_session=True)`. What happens to `base`'s history?

<details><summary>Answer</summary>

Nothing. The fork gets a new session ID and its own history; `base` is unchanged and can still be resumed.

</details>

**5.** Which command continues your named investigation "billing-bug" tomorrow?

<details><summary>Answer</summary>

`claude --resume billing-bug`.

</details>
