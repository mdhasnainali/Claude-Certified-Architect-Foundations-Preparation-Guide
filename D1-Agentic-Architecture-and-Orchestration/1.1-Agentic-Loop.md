# 1.1 Agentic Loop

## Goal
After this you can write a tool loop that stops for the right reason, and spot the three wrong stop signals the exam loves. *(Task statement 1.1)*

## Guess first
1. Claude replies with the text "Let me check that order for you." **and** a tool call in the same response. Is the agent done?
2. Your loop stops after 5 rounds to save money. A refund case needs 7 tool calls. What does the customer get?

## Idea
An agent is a model that calls tools in a loop. **Your code drives the loop:**

1. Send `messages` + tool definitions to Claude.
2. Read `stop_reason` on the response.
3. `"tool_use"` → Claude wants tools. Run every `tool_use` block. Append Claude's whole response as an `assistant` message. Then append **one** `user` message with all the `tool_result` blocks. Go to step 1.
4. `"end_turn"` → Claude is finished. Show the final text.
 
The API is stateless. Claude remembers nothing between calls. **The `messages` list is the memory.** Tool results go into it, so on the next call Claude reads them and decides the next step. That is why you append the full `response.content`, not only its text: it holds the `tool_use` blocks with their `id`. Each `tool_result` must point back to one of them with `tool_use_id`.

*In Python terms:* it's like calling `next()` on a generator until it raises `StopIteration`. The "done" signal is a field (`stop_reason`), not something you guess from the text.

**Model-driven vs pre-configured.** In an agent, Claude picks the next tool from the context (model-driven). In a workflow, your code fixes the order in advance (a decision tree or a fixed sequence). The loop above is model-driven. When the order must never change, use code instead — see [1.4 Enforcement and Handoffs](1.4-Enforcement-and-Handoffs.md).

Other `stop_reason` values you should recognise:

| `stop_reason`   | Meaning                      | What the loop does                                    |
| --------------- | ---------------------------- | ----------------------------------------------------- |
| `end_turn`      | Finished normally            | Stop, use the answer                                  |
| `tool_use`      | Wants client tools run       | Run tools, send results, loop                         |
| `max_tokens`    | Output was cut off           | Not success: raise `max_tokens` or mark truncated     |
| `pause_turn`    | Server-tool loop paused      | Append the response and send again (no new user text) |
| `refusal`       | Claude declined              | Not success: handle it                                |
| `stop_sequence` | Hit one of your stop strings | App-specific                                          |

**Three wrong stop signals (exam favourites):**
- **Parsing the text** for "done", "finished", "anything else?". Text is for humans, not a control signal.
- **Stopping when a text block appears.** Claude often writes a short note *and* a tool call in one response. You stop before the tool runs.
- **An iteration cap as the main exit.** It cuts real work in half and the user gets nothing. A cap is only a safety net (with an alert), never the normal way to finish.

## Code

**File:** [`codes/1_1_agentic_loop.py`](codes/1_1_agentic_loop.py) · run `make run 1_1_agentic_loop`

Python 3.13+, `anthropic` 2.14. Needs `ANTHROPIC_API_KEY`. Uses Haiku, so a run costs well under a cent.
Save as `1_1_agentic_loop.py`, run `uv run --with anthropic python 1_1_agentic_loop.py`. It prints the exact JSON of every request and response, so you see the loop on the wire.

```python
# 1_1_agentic_loop.py — Python 3.13+, anthropic 2.14. Run: uv run --with anthropic python 1_1_agentic_loop.py
import json

import anthropic
from anthropic.types import MessageParam, ToolParam, ToolResultBlockParam

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY
TOOLS: list[ToolParam] = [
    {
        "name": "get_order_status",
        "description": "Look up ONE order by ID (format ORD-<n>). Returns its status.",
        "input_schema": {
            "type": "object",
            "properties": {"order_id": {"type": "string"}},
            "required": ["order_id"],
        },
    }
]
ORDERS = {"ORD-1": "shipped, arrives in 2 days", "ORD-2": "refunded on 20 Nov"}
messages: list[MessageParam] = [
    {"role": "user", "content": "Where are my orders ORD-1 and ORD-2?"}
]

def show(title: str, body: bytes) -> None:
    print(f"\n{'=' * 20} {title} {'=' * 20}")
    print(json.dumps(json.loads(body), indent=2, ensure_ascii=False))

for turn in range(1, 11):  # safety net only; stop_reason is the real exit
    raw = client.messages.with_raw_response.create(
        model="claude-haiku-5-5", max_tokens=4000, tools=TOOLS, messages=messages
    )
    # Exact JSON bodies on the wire. Headers skipped: they carry the API key.
    req = raw.http_request
    show(f"TURN {turn} REQUEST: {req.method} {req.url}", req.content)
    show(f"TURN {turn} RESPONSE: {raw.status_code}", raw.http_response.content)
    resp = raw.parse()  # same body as a typed Message object

    messages.append({"role": "assistant", "content": resp.content})  # keep tool_use
    if resp.stop_reason == "end_turn":
        text = "".join(b.text for b in resp.content if b.type == "text")
        print(f"\n{'=' * 20} FINAL ANSWER {'=' * 20}\n{text}")
        break
    if resp.stop_reason != "tool_use":
        raise RuntimeError(f"unexpected stop: {resp.stop_reason}")
    results: list[ToolResultBlockParam] = [
        {
            "type": "tool_result",
            "tool_use_id": b.id,
            "content": ORDERS.get(str(b.input["order_id"]), "error: no such order"),
        }
        for b in resp.content
        if b.type == "tool_use"
    ]
    messages.append({"role": "user", "content": results})  # all results, ONE message
else:
    raise RuntimeError("no end_turn after 10 turns")
```

<details><summary>Other fields in the response (look-up)</summary>

The loop needs only three: `content`, `stop_reason`, and `usage.input_tokens` / `output_tokens`. In this run the rest are `null` or a default. What each one is for:

| Field | What it tells you | Why `null` / default here |
|---|---|---|
| `stop_sequence` | Which of your `stop_sequences` strings Claude hit | You sent none |
| `stop_details` | Extra detail on the stop. Today only for `refusal`: `category` + `explanation` | No refusal |
| `container` | The sandbox where Anthropic ran code (code execution tool, Skills): `id`, `expires_at`, `skills`. Send `container=<id>` next time to reuse its files | Your tool runs on your machine, so no container |
| `diagnostics` | Prompt-cache debug report (beta). `cache_miss_reason` says why the cache missed: `system` changed, `tools` changed, old `messages` edited … | You didn't ask for it (`diagnostics={"previous_message_id": …}`) |
| `usage.cache_creation_input_tokens` · `cache_read_input_tokens` · `cache_creation` | Prompt caching: tokens written to / read from the cache. Total input = `input_tokens` + these two | No `cache_control`, so 0 |
| `usage.output_tokens_details.thinking_tokens` | How many of the `output_tokens` were Claude's hidden thinking | Haiku 5.5 thinks by default, so it can be > 0 |
| `usage.server_tool_use` | How many `web_search` / `web_fetch` calls Anthropic ran for you | Only your own tool, no server tools |
| `usage.service_tier` | Which capacity pool served you: `standard`, `priority` (paid reserved capacity), `batch` (Batches API: half price, not instant) | Normal request → `standard` |
| `usage.inference_geo` | Region where the model ran. Send `inference_geo="us"` to keep it in the US | No setting → your workspace default (`global` = any region) |
| `usage.speed` | `standard` or `fast`. Fast mode = same model, up to 2.5× faster output, higher price (`speed="fast"`, some models only, e.g. Opus 5.5) | Not asked → `standard` |

</details>

**Predict first, then change and run:**
1. Delete the line `messages.append({"role": "user", "content": results})`. What happens on the next call?
2. Change `if resp.stop_reason == "end_turn":` to `if any(b.type == "text" for b in resp.content):`. Keep the print and the break inside it, and delete the `!= "tool_use"` check. Can this stop too early?
3. Change `range(1, 11)` to `range(1, 2)`. What does the user see?
4. Compare the two `usage.input_tokens` values. Why is turn 2 bigger?

<details><summary>Answers</summary>

1. A 400 error (`anthropic.BadRequestError`, `invalid_request_error`): every `tool_use` must be followed by its `tool_result` in the next user message. The error comes from `create`, so the TURN 2 REQUEST dump never prints. The loop has no memory except `messages`.
2. Yes, anti-pattern #2. If a response has a short text note next to its tool_use blocks, the loop ends before the tools run, and the note prints as the FINAL ANSWER. Look at TURN 1 RESPONSE: in this run Haiku sent only tool_use blocks, so the bug hides in your test. Another model or prompt can add the note. Still a bug.
3. The TURN 1 dumps print. Then the loop ends with stop_reason `tool_use`, and the `for … else` branch raises `RuntimeError: no end_turn after 10 turns`. The message always says 10, because the number is typed into the code. There is no final answer, but now there is a loud error instead of a silent one. The cap is a safety net, not the exit (anti-pattern #3).
4. The API keeps no state. Turn 2 sends everything again: the question, the tool_use blocks, the tool_results and the tool schema. So each loop turn costs more input tokens than the one before.

</details>

## When to use · gotchas
- **Use the loop** when the steps can't be known up front (open-ended tasks). **Use fixed code** (a workflow) when the order is known or must be guaranteed.
- Send **all** tool results from one response in **one** user message. Splitting them teaches Claude to stop making parallel calls.
- Put the `tool_result` blocks first in that message. Don't add text after them — it can cause empty `end_turn` replies.
- A tool failed? Still send a `tool_result`, with `"is_error": True` and a clear message. Never drop it.
- Keep a high iteration cap and a budget as guardrails, with an alert when hit. Never as the normal exit.
- In real projects the SDK's Tool Runner (`client.beta.messages.tool_runner`) or the Claude Agent SDK's `query()` runs this loop for you. The Agent SDK ends a run with a `ResultMessage` whose `subtype` is `success`, `error_max_turns`, `error_max_budget_usd`, … The exam still expects you to know the manual loop.

## Try it
*≤ 10 min.* Add a second tool `cancel_order(order_id)`. It always fails for shipped orders. Return that failure with `"is_error": True`. Ask "Please cancel ORD-1." What does Claude tell the user?

<details><summary>Solution</summary>

Add the tool to `TOOLS` and branch on the name when you build results:
```python
TOOLS.append({"name": "cancel_order",
              "description": "Cancel ONE order that has not shipped yet (format ORD-<n>).",
              "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}},
                               "required": ["order_id"]}})

def run(block):
    if block.name == "cancel_order":
        return {"type": "tool_result", "tool_use_id": block.id, "is_error": True,
                "content": "Cannot cancel: ORD-1 already shipped. Offer a return instead."}
    return {"type": "tool_result", "tool_use_id": block.id,
            "content": ORDERS.get(block.input["order_id"], "error: no such order")}

# in the loop: results = [run(b) for b in resp.content if b.type == "tool_use"]
```
Claude reads the error and explains that the order already shipped, then offers a return. A clear error lets Claude recover instead of retrying blindly.

</details>

## Quiz
**1.** Your support agent sometimes ends after "Let me pull up your account" and never calls the tool. The loop code is `if response.content[-1].type == "text": break`. Best fix? A) Add "always finish with a summary" to the system prompt · B) Loop while `stop_reason == "tool_use"`, stop on `"end_turn"` · C) Raise the iteration cap to 50 · D) Stop when the text contains "anything else?"

<details><summary>Answer</summary>

**B.** `stop_reason` is the only reliable control signal. A and D still read text as a signal. C changes nothing about the wrong check.

</details>

**2.** Why do you append `response.content` to `messages`, and not only the text?

<details><summary>Answer</summary>

The API is stateless. The full content holds the `tool_use` blocks and their `id`s. The next request must contain them, followed by matching `tool_result` blocks, or the API rejects it. It also keeps Claude's reasoning about what it already tried.

</details>

**3.** `stop_reason` is `"max_tokens"` and the last block is a half-written `tool_use`. What should the loop do?

<details><summary>Answer</summary>

Treat it as not finished. Don't run a partial tool call. Retry that turn with a higher `max_tokens`.

</details>

**4.** To save cost, a team makes `max_iterations=3` the way their agent finishes. Complex refund cases now end with no answer. What is the real mistake, and what controls cost instead?

<details><summary>Answer</summary>

The cap is used as the primary stopping mechanism. Stop on `end_turn`; keep a high cap only as a guardrail. Control cost with a budget limit, lower effort, smaller tool outputs, or a cheaper model for simple steps.

</details>

**5.** "The customer's identity must be verified before any refund." Model-driven tool choice, or a pre-configured sequence?

<details><summary>Answer</summary>

Pre-configured / programmatic. The order must never change, and a model-driven choice has a non-zero failure rate. See 1.4.

</details>
