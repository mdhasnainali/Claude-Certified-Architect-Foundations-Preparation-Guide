# 4.1 Explicit Criteria

## Goal
After this you can write review prompts with explicit criteria that cut false positives, and decide which noisy categories to pause. *(Task statement 4.1)*

## Guess first
1. Your PR review bot is noisy. A teammate adds "Be conservative. Only report high-confidence findings." Will precision improve much?
2. 70% of the bot's comments are about naming style and get dismissed. What happens to the 30% that are real bugs?

## Idea
**Vague instructions don't change behaviour much.** "Check that comments are accurate", "be conservative", "only high-confidence findings" — Claude can't tell what *you* count as a problem. **Explicit, categorical criteria** can:

| Vague | Explicit |
|---|---|
| "Check that comments are accurate" | "Flag a comment only when the behaviour it claims contradicts what the code does" |
| "Report important issues" | "Report: bugs that give wrong results, crashes, security holes. Skip: naming, formatting, patterns used consistently in this repo" |
| "Rate severity" | "**high** = data loss / security / wrong money amount (e.g. `float` for prices); **medium** = crash on rare input; **low** = misleading message" — each with a short code example |

Anthropic's rule of thumb: treat Claude like a brilliant new colleague who doesn't know your norms. If a colleague would be confused by the prompt, Claude will be too.

**False positives destroy trust.** When one category is mostly noise, developers stop reading *all* comments — including the accurate security findings. So:
1. Measure precision **per category** (fixed vs dismissed).
2. **Temporarily disable** high-false-positive categories to restore trust.
3. Rewrite those categories' criteria (with examples), test, then turn them back on.

**Severity needs anchors.** Define each level with concrete code examples, or the same issue gets "high" in one PR and "low" in the next.

*In Python terms:* a vague prompt is like `if looks_bad(x):` — nobody knows what it checks. Explicit criteria are like a written `def is_bug(x) -> bool` with named conditions.

## Code

**File:** [`codes/4_1_fp_report.py`](codes/4_1_fp_report.py) · run `make run 4_1_fp_report`

Python 3.13+, offline, no API key. Save as `4_1_fp_report.py`, run `python3 4_1_fp_report.py`.

```python
# 4_1_fp_report.py — Python 3.13+, offline. Which review categories destroy trust? Measure, then act.
from collections import Counter

# one row per comment the review bot posted last month: (category, what the developer did)
review_log = (
    [("sql-injection", "fixed")] * 9
    + [("sql-injection", "dismissed")] * 1
    + [("null-deref", "fixed")] * 14
    + [("null-deref", "dismissed")] * 4
    + [("naming-style", "fixed")] * 3
    + [("naming-style", "dismissed")] * 27
    + [("comment-accuracy", "fixed")] * 2
    + [("comment-accuracy", "dismissed")] * 18
)

posted_count = Counter(category for category, _ in review_log)
fixed_count = Counter(
    category for category, developer_action in review_log if developer_action == "fixed"
)
for category in posted_count:
    precision = fixed_count[category] / posted_count[category]
    recommendation = (
        "keep" if precision >= 0.6 else "PAUSE category, rewrite its criteria"
    )
    print(
        f"{category:17} posted={posted_count[category]:3}  "
        f"precision={precision:4.0%}  → {recommendation}"
    )
print(
    f"overall precision {sum(fixed_count.values()) / len(review_log):.0%}: most comments are noise, so developers ignore all of them"
)
```

Expected output:
```
sql-injection     posted= 10  precision= 90%  → keep
null-deref        posted= 18  precision= 78%  → keep
naming-style      posted= 30  precision= 10%  → PAUSE category, rewrite its criteria
comment-accuracy  posted= 20  precision= 10%  → PAUSE category, rewrite its criteria
overall precision 36%: most comments are noise, so developers ignore all of them
```
Pausing two categories lifts overall precision from 36% to 82% (23 of 28) — the real findings become visible again.

The explicit review prompt that replaces "be conservative":
```text
Review this diff. REPORT only:
- bugs that produce wrong results (example: `price * 0.1` on a float money value),
- crashes on plausible input (None, empty list, missing key),
- security issues (SQL built with f-strings, secrets in code).
SKIP: naming, formatting, import order, and any pattern used the same way elsewhere in this repo.
Flag a comment only when the behaviour it describes contradicts what the code does.
Severity: high = security / data loss / wrong money; medium = crash on rare input; low = misleading text.
```

**Predict first, then change and run:** set the pause threshold to `0.8`. Which category is paused now, and is that a good idea?

<details><summary>Answer</summary>

`null-deref` (78%) is paused too. That hides a mostly useful category — 14 real bugs a month. Pause categories that are mostly noise, not ones that are merely imperfect.

</details>

## When to use · gotchas
- "Be conservative" / "high confidence only" / "be careful" are not criteria. Name what to report and what to skip.
- Define severity with examples, or labels drift between runs.
- Track precision **per category**, not one overall number (same lesson as [5.5 Human Review and Confidence](../D5-Context-Management-and-Reliability/5.5-Human-Review-and-Confidence.md)).
- Pausing a noisy category is a trust repair step, not the end: rewrite its criteria and re-enable it.
- Exam distractor: "add 'only report findings you're 90% sure about'". Confidence filtering ≠ clear criteria.

## Quiz
**1.** A review bot has many false positives. Which change most improves precision? A) Add "be conservative" · B) Add "only report findings with confidence above 90%" · C) Define which issue types to report and which to skip, with examples · D) Use a larger model

<details><summary>Answer</summary>

**C.** Explicit categorical criteria. A and B are vague and barely change behaviour.

</details>

**2.** Developers ignore the bot's security warnings even though they are accurate. Likely cause?

<details><summary>Answer</summary>

Other categories have high false-positive rates, so developers distrust all comments. Pause the noisy categories, fix their criteria.

</details>

**3.** The same issue gets "high" severity in one PR and "low" in another. Fix?

<details><summary>Answer</summary>

Define each severity level explicitly with concrete code examples.

</details>

**4.** Rewrite "check that comments are accurate" as an explicit criterion.

<details><summary>Answer</summary>

"Flag a comment only when the behaviour it claims contradicts the actual code behaviour."

</details>

**5.** Why does a high false-positive rate in one category hurt the others?

<details><summary>Answer</summary>

Trust is shared: developers stop reading the bot's comments in general, so accurate findings are ignored too.

</details>
