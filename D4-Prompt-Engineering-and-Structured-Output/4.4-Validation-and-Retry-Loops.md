# 4.4 Validation and Retry Loops

## Goal
After this you can validate extractions in code, retry with specific error feedback, and tell when a retry can't help. *(Task statement 4.4)*

## Guess first
1. An extraction fails validation. You retry with the same prompt. Good idea?
2. The invoice's line items add up to $200, but the document's printed total says $210. Will a retry fix it?

## Idea
**Two kinds of error:**
- **Schema syntax errors** — broken JSON, wrong types. Tool use with a strict schema removes these ([4.3 Structured Output with Tool Use](4.3-Structured-Output-with-Tool-Use.md)).
- **Semantic errors** — valid JSON, wrong meaning: items don't sum to the total, a date in the wrong format or field. You catch these with **your own validation** (e.g. Pydantic validators).

**Retry with error feedback.** Don't resend the same prompt. Send a follow-up with:
1. the **original document**,
2. the **failed extraction**,
3. the **specific validation errors** ("invoice_date: must be YYYY-MM-DD").
Claude then corrects exactly what was wrong.

**Know when retry is useless.** Retries fix **format and structure** mistakes. They can't fix **missing information** — if the due date is only in a contract that wasn't provided, asking again just invites an invented value. Return null and route to a human or fetch the other document.

**Self-checking fields.** Ask for `calculated_total` (sum of items) next to `stated_total` (what the document prints), and a `conflict_detected` boolean. A conflict in the *source* is not an extraction error — flag it for review instead of retrying.

**Feedback loop for reviews.** Add a `detected_pattern` field to each finding (e.g. `"float-money"`, `"bare-except"`). When developers dismiss findings, you can see *which patterns* cause false positives and fix those criteria ([4.1 Explicit Criteria](4.1-Explicit-Criteria.md)).

*In Python terms:* `json.loads()` succeeding is the strict schema. `pydantic` validators and `assert sum(items) == total` are the semantic checks — and they belong in your code.

```python
# 4_4_validate_retry.py — part 1: schema + semantic checks. pydantic 2, offline.
import json
from pydantic import BaseModel, ValidationError, field_validator, model_validator

class LineItem(BaseModel):
    description: str
    amount: float

class Invoice(BaseModel):
    invoice_date: str
    items: list[LineItem]
    stated_total: float
    # computed here, then compared with the total the document states
    calculated_total: float | None = None
    conflict_detected: bool = False

    @field_validator("invoice_date")
    @classmethod
    def check_iso_date(cls, value: str) -> str:
        if len(value) != 10 or value[4] != "-" or value[7] != "-":
            raise ValueError("must be YYYY-MM-DD")
        return value

    @model_validator(mode="after")
    def check_totals(self):
        self.calculated_total = round(sum(item.amount for item in self.items), 2)
        self.conflict_detected = abs(self.calculated_total - self.stated_total) > 0.01
        return self
```

```python
# 4_4_validate_retry.py — part 2: build the retry prompt, then check the fixed extraction
DOCUMENT = "Invoice, 3 Nov 2026. Hosting $120.00. Support $80.00. TOTAL DUE: $210.00"
first_extraction = {
    "invoice_date": "3 Nov 2026",
    "stated_total": 210,
    "items": [
        {"description": "Hosting", "amount": 120},
        {"description": "Support", "amount": 80},
    ],
}
try:
    Invoice(**first_extraction)
except ValidationError as validation_error:
    error_lines = [
        f"{'.'.join(map(str, error['loc']))}: {error['msg']}"
        for error in validation_error.errors()
    ]
    print(
        f"<document>\n{DOCUMENT}\n</document>\n<previous_extraction>\n{json.dumps(first_extraction)}\n"
        "</previous_extraction>\nFix ONLY these errors and return the full extraction:\n- "
        + "\n- ".join(error_lines)
    )

retried_extraction = {
    **first_extraction,
    "invoice_date": "2026-11-03",
}  # what the retry returns
invoice = Invoice(**retried_extraction)
print(
    f"\nvalid. calculated_total={invoice.calculated_total} stated_total={invoice.stated_total} "
    f"conflict_detected={invoice.conflict_detected}"
)
```

Expected output:
```
<document>
Invoice, 3 Nov 2026. Hosting $120.00. Support $80.00. TOTAL DUE: $210.00
</document>
<previous_extraction>
{"invoice_date": "3 Nov 2026", "stated_total": 210, "items": [{"description": "Hosting", "amount": 120}, {"description": "Support", "amount": 80}]}
</previous_extraction>
Fix ONLY these errors and return the full extraction:
- invoice_date: Value error, must be YYYY-MM-DD

valid. calculated_total=200.0 stated_total=210.0 conflict_detected=True
```
The date error is fixable → retry with feedback. The $200 vs $210 conflict is in the **document itself** → a retry can't fix it; route to a human.

**Predict first, then check:** the document is changed to "TOTAL DUE: see attached statement". `stated_total` is required. What happens if you retry 3 times?

<details><summary>Answer</summary>

The information isn't in the document, so retries can't find it — at best you get errors three times, at worst an invented number. Make `stated_total` nullable, accept null, and flag it for review.

</details>

## When to use · gotchas
- Retry **with** the document, the failed output and the exact errors — never a blind resend.
- Cap retries (1–2). If the same error repeats, the information is probably missing or ambiguous.
- Separate *extraction errors* (retry) from *source conflicts* (flag) from *missing data* (null + review).
- Validators belong in code. Asking Claude "double-check your math" is still probabilistic.
- Log `detected_pattern` on findings so dismissals turn into prompt fixes.

## Try it
*≤ 10 min.* Write `should_retry(error_lines: list[str], document: str) -> bool`: retry for format errors, but not when the error is about a value that the document doesn't contain (hint: a field-missing error where the field's keyword isn't in the document).

<details><summary>Solution</summary>

```python
def should_retry(error_lines: list[str], document: str) -> bool:
    for error in error_lines:
        field = error.split(":")[0].split(".")[-1]       # e.g. "stated_total"
        keyword = {"stated_total": "total", "invoice_date": "invoice", "due_date": "due date"}.get(field, field)
        if "Field required" in error and keyword.lower() not in document.lower():
            return False                                   # absent from source → retry won't help
    return True

print(should_retry(["invoice_date: Value error, must be YYYY-MM-DD"], DOCUMENT))     # True
print(should_retry(["due_date: Field required"], DOCUMENT))                           # False
```

</details>

## Quiz
**1.** An extraction fails validation because line items don't match the total. The current loop resends the original prompt. Better? A) Resend with temperature 0 · B) Send the document, the failed extraction and the specific validation errors · C) Increase max_tokens · D) Switch model

<details><summary>Answer</summary>

**B.** Retry-with-error-feedback gives Claude what it needs to correct the exact problem.

</details>

**2.** When will a retry not help?

<details><summary>Answer</summary>

When the required information is absent from the source (e.g. it's in another document that wasn't provided). Format and structure errors are fixable; missing data isn't.

</details>

**3.** Strict tool use is enabled. Which errors are still possible?

<details><summary>Answer</summary>

Semantic ones — values that don't add up, values in the wrong field, wrong but well-typed data.

</details>

**4.** Why extract both `calculated_total` and `stated_total`?

<details><summary>Answer</summary>

To detect discrepancies automatically: a mismatch is flagged (`conflict_detected`) for review instead of silently trusting one number.

</details>

**5.** Developers dismiss many review findings. What field helps you find out why?

<details><summary>Answer</summary>

`detected_pattern` on each finding — so you can analyse which code constructs cause false positives.

</details>
