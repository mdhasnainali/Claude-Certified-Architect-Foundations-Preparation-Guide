# 4.6 Multi-Pass Review

## Goal
After this you can design review architectures that catch more real bugs: an independent reviewer instead of self-review, per-file + integration passes, and confidence-based routing. *(Task statement 4.6)*

## Guess first
1. Claude just wrote a function. You ask the **same session**: "Now review your code carefully." Will it find its own subtle bugs?
2. Does turning on extended thinking for that self-review solve the problem?

## Idea
**Self-review is weak.** The generating session keeps its own reasoning in context: *why* it chose that approach. So it tends to confirm its decisions instead of questioning them. Asking it to "review carefully", or giving it more thinking, doesn't remove that anchor.

**An independent review instance works better.** A **new** request (new session) that gets only the code and the review criteria — none of the generator's reasoning — catches subtle issues more often. This is also why, in CI, a separate Claude run should review the code another Claude run generated ([1.7 Sessions Resume and Fork](../D1-Agentic-Architecture-and-Orchestration/1.7-Sessions-Resume-and-Fork.md) on session isolation). Anthropic's "self-correction" chain uses the same idea: generate → review against criteria → refine, each as a **separate call** so you can inspect each step.

**Multi-pass for big changes** (from [1.6 Task Decomposition](../D1-Agentic-Architecture-and-Orchestration/1.6-Task-Decomposition.md)): per-file passes for local issues + a separate integration pass for cross-file data flow. One pass over many files dilutes attention and produces contradictions.

**Verification pass with confidence → routing.** Have the reviewer return each finding with a severity and a self-reported confidence. Use them to **route review effort**: high-severity, high-confidence findings go straight to the PR; the rest to a human triage queue. Calibrate the threshold on labeled history first — raw self-confidence is not reliable on its own ([5.5 Human Review and Confidence](../D5-Context-Management-and-Reliability/5.5-Human-Review-and-Confidence.md)).

*In Python terms:* it's code review practice. The author re-reading their own PR misses things a teammate sees in five minutes — the teammate doesn't share the author's assumptions.

## Code

**File:** [`codes/4_6_review_pass.py`](codes/4_6_review_pass.py) · run `make run 4_6_review_pass`

Python 3.13+, `anthropic` 2.13 (with Pydantic). Needs `ANTHROPIC_API_KEY`; 2 calls. Save as `4_6_review_pass.py`, run `uv run --with anthropic python 4_6_review_pass.py`.

```python
# 4_6_review_pass.py — anthropic 2.13. Run: uv run --with anthropic python 4_6_review_pass.py
from typing import Literal
import anthropic
from pydantic import BaseModel

client = anthropic.Anthropic()

class Finding(BaseModel):
    line: int
    issue: str
    severity: Literal["high", "medium", "low"]
    confidence: (
        float  # self-reported: use it for routing only after calibration (lesson 5.5)
    )

class Review(BaseModel):
    findings: list[Finding]

gen = client.messages.create(
    model="claude-haiku-5-5",
    max_tokens=4000,
    messages=[
        {
            "role": "user",
            "content": "Write a Python function parse_price(s) that turns '$1,299.50' into 1299.5. Code only.",
        }
    ],
)
code = next(b.text for b in gen.content if b.type == "text")

# Independent reviewer: a NEW request with only the code and the criteria, none of the generator's reasoning
review = client.messages.parse(
    model="claude-haiku-5-5",
    max_tokens=4000,
    output_format=Review,
    messages=[
        {
            "role": "user",
            "content": "Review this code. Report only real bugs: wrong results or crashes on "
            "plausible inputs (negative, empty, no '$', other currencies). Skip style.\n<code>\n"
            + code
            + "\n</code>",
        }
    ],
)
for f in review.parsed_output.findings:
    route = (
        "post as PR comment"
        if f.severity == "high" and f.confidence >= 0.8
        else "human triage queue"
    )
    print(f"line {f.line} [{f.severity}, {f.confidence:.2f}] {f.issue} → {route}")
```

Possible output (findings depend on the generated code):
```
line 3 [high, 0.90] '-$5.00' becomes 5.0: the minus sign is dropped → post as PR comment
line 2 [medium, 0.70] empty string raises ValueError with an unclear message → human triage queue
line 4 [low, 0.55] '€12,50' (comma decimal) parses as 1250.0 → human triage queue
```

**Predict first, then change and check:** instead of a new request, append the review prompt as a follow-up turn in the generator's conversation (`messages=[gen prompt, gen answer, review prompt]`). Run both versions a few times. Which finds more edge-case bugs?

<details><summary>Answer</summary>

Usually the independent request. The follow-up review shares the generator's context and tends to defend its own choices; the fresh reviewer has no such anchor. (Results vary per run — compare over several runs, not one.)

</details>

## When to use · gotchas
- Generated code that matters → review it in a **separate** instance, without the generator's reasoning.
- "Review your own work carefully" and "think harder" are weaker than independence.
- Large PRs → per-file passes + integration pass; not one giant pass, not "bigger context window".
- Don't require consensus of several runs to report a bug — it hides real bugs that show up only sometimes.
- Confidence routing needs calibration data; start with severity + confidence and adjust thresholds from what reviewers accept.

You review code that another system generated. You receive only the diff and the

## Quiz
**1.** Claude generates code, then in the same session reviews it and misses subtle bugs. Most effective fix? A) Add "review very critically" · B) Enable extended thinking for the review · C) Review with a second, independent Claude instance that doesn't see the generator's reasoning · D) Run the self-review 3 times

<details><summary>Answer</summary>

**C.** Independent instances beat self-review instructions and more thinking — the generator's context anchors it.

</details>

**2.** Why is the generating session a weak reviewer of its own code?

<details><summary>Answer</summary>

It keeps its reasoning context from generation, so it's less likely to question its own decisions.

</details>

**3.** A 14-file PR gets uneven, contradictory review comments. Architecture fix?

<details><summary>Answer</summary>

Per-file local passes plus a separate cross-file integration pass.

</details>

**4.** What is the point of having the reviewer report confidence per finding?

<details><summary>Answer</summary>

Routing: post high-severity/high-confidence findings directly, send the rest to human triage — after calibrating the threshold.

</details>

**5.** "Only report a bug if 2 of 3 review runs find it." Good idea?

<details><summary>Answer</summary>

No — it suppresses real bugs that are caught intermittently. Improve criteria and architecture instead.

</details>
