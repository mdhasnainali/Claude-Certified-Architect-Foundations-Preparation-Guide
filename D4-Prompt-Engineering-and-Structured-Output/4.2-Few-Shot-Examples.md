# 4.2 Few-Shot Examples

## Goal
After this you can write a few targeted examples that make output consistent, teach Claude your judgment on ambiguous cases, and reduce made-up values in extraction. *(Task statement 4.2)*

## Guess first
1. You wrote a full page of formatting rules. Output is still inconsistent. What is the strongest next step?
2. Should few-shot examples cover the easy, typical cases or the tricky ones?

## Idea
**Few-shot examples are the most reliable way to get consistent, usable output** when detailed instructions alone still give mixed results. Anthropic: examples are "one of the most reliable ways to steer Claude's output format, tone, and structure".

What good examples do:
- **Show the exact output shape** — e.g. every finding as `location · issue · severity · suggested fix`.
- **Show judgment on ambiguous cases** — which tool for an unclear request, when a test gap at branch level matters — **with a short reason** why this choice beats the plausible alternative.
- **Generalise.** Claude learns the *pattern* behind your examples and applies it to new cases, instead of matching only the cases you listed.
- **Separate fine from wrong.** Pair an acceptable code pattern with a real bug → fewer false positives.
- **Cut hallucination in extraction.** Show informal measurements ("a couple of", "2–3 cups"), different document layouts (inline citations vs a bibliography, methods section vs details scattered in the text), and fields that are **absent** — with `null`, not an invented value.

**How many?** The exam says **2–4 targeted examples** for ambiguous scenarios; Anthropic's docs suggest 3–5. Both mean: few, chosen for the hard cases, varied enough that Claude doesn't copy an accidental pattern. Wrap them in `<example>` tags.

*In Python terms:* examples are like doctests. A docstring describes the rule; three good `>>>` lines show it — including the edge case.

## Code

**File:** [`codes/4_2_fewshot.py`](codes/4_2_fewshot.py) · run `make run 4_2_fewshot`

Python 3.13+, `anthropic` 2.13 (with its Pydantic support). Needs `ANTHROPIC_API_KEY`; 8 small calls. Save as `4_2_fewshot.py`, run `uv run --with anthropic python 4_2_fewshot.py`.

```python
# 4_2_fewshot.py — anthropic 2.13. Run: uv run --with anthropic python 4_2_fewshot.py
import anthropic
from pydantic import BaseModel

client = anthropic.Anthropic()

class Quantity(BaseModel):
    quantity: float | None  # None when the text gives no number — never invent one
    unit: str | None
    approximate: bool

FEW_SHOT_EXAMPLES = """<examples>
<example>"a couple of eggs" → {"quantity": 2, "unit": "piece", "approximate": true}
Why: "a couple" means about 2; eggs are counted in pieces.</example>
<example>"salt to taste" → {"quantity": null, "unit": null, "approximate": true}
Why: no amount is stated; inventing "1 pinch" would be a hallucination.</example>
<example>"2-3 cups flour" → {"quantity": 2.5, "unit": "cup", "approximate": true}
Why: for a range, use the midpoint and mark it approximate.</example>
</examples>"""
INGREDIENT_LINES = [
    "a handful of walnuts",
    "pepper, as needed",
    "1/2 lb butter",
    "4-6 cloves garlic",
]

for examples in ("", FEW_SHOT_EXAMPLES):
    print("FEW-SHOT" if examples else "ZERO-SHOT")
    for ingredient in INGREDIENT_LINES:
        response = client.messages.parse(
            model="claude-haiku-5-5",
            max_tokens=2000,
            output_format=Quantity,
            messages=[
                {
                    "role": "user",
                    "content": f"{examples}\nExtract the quantity from: {ingredient!r}",
                }
            ],
        )
        print(f"  {ingredient:22} → {response.parsed_output.model_dump()}")
```

Possible output (zero-shot answers vary between runs — watch "as needed" and the range):
```
ZERO-SHOT
  a handful of walnuts   → {'quantity': 1.0, 'unit': 'handful', 'approximate': True}
  pepper, as needed      → {'quantity': 1.0, 'unit': 'pinch', 'approximate': True}
  1/2 lb butter          → {'quantity': 0.5, 'unit': 'lb', 'approximate': False}
  4-6 cloves garlic      → {'quantity': 4.0, 'unit': 'clove', 'approximate': True}
FEW-SHOT
  a handful of walnuts   → {'quantity': 1.0, 'unit': 'handful', 'approximate': True}
  pepper, as needed      → {'quantity': None, 'unit': None, 'approximate': True}
  1/2 lb butter          → {'quantity': 0.5, 'unit': 'lb', 'approximate': False}
  4-6 cloves garlic      → {'quantity': 5.0, 'unit': 'clove', 'approximate': True}
```
None of the four test lines is in the examples. Few-shot still applies the *rules* behind them (null for "as needed", midpoint for ranges) — that's generalisation.

**Predict first, then change and run:** delete the `Why:` lines from the examples. What changes?

<details><summary>Answer</summary>

Often little on these lines — but on new borderline inputs Claude is less sure which rule an example meant. The reason tells Claude *why* one answer beats the plausible alternative, which is what lets it generalise.

</details>

## When to use · gotchas
- Use few-shot when instructions alone give **inconsistent** format or judgment. Fix unclear instructions first (4.1).
- Target **ambiguous** cases; easy cases teach little.
- Vary the examples, or Claude copies accidental features (same length, same wording).
- Show **absent** data as `null` in at least one example — the strongest guard against invented values.
- Examples cost tokens on every call. Few, sharp examples beat many.
- Exam: for *tool selection* problems the first fix is better tool descriptions (2.1), not a pile of few-shot examples.

## Quiz
**1.** Detailed instructions still produce findings in different formats. Most effective fix? A) Make the instructions longer · B) Add 2–4 examples showing the exact format (location, issue, severity, fix) · C) Lower temperature · D) Post-process with regex

<details><summary>Answer</summary>

**B.** Few-shot examples are the most effective way to get consistent format when instructions alone fail.

</details>

**2.** An extraction model fills `due_date` even when the document has none. Besides schema design, what helps?

<details><summary>Answer</summary>

Few-shot examples from varied documents where a missing field is returned as `null`.

</details>

**3.** Why include a short reason in each example?

<details><summary>Answer</summary>

It shows why one choice beats a plausible alternative, so Claude can generalise the judgment to new cases.

</details>

**4.** The bot flags a safe, repo-wide pattern as a bug. How can examples help?

<details><summary>Answer</summary>

Add an example that shows the acceptable pattern next to a real issue, explaining the difference — fewer false positives.

</details>

**5.** Should examples mostly cover typical easy inputs?

<details><summary>Answer</summary>

No — target the ambiguous and edge cases, and keep them varied.

</details>
