# 4.3 Structured Output with Tool Use

## Goal
After this you can get guaranteed schema-shaped output with a tool + JSON schema, design a schema that doesn't push Claude to invent data, and know what the schema can't guarantee. *(Task statement 4.3)*

## Guess first
1. Your prompt says "Return valid JSON". 2% of responses fail to parse. What makes parse errors impossible?
2. A field is `required`, but the document doesn't contain it. What will Claude put there?

## Idea
**Tool use + JSON schema = the most reliable way to get structured output.** Define an "extraction tool" whose `input_schema` *is* the shape you want. Claude's `tool_use.input` is your data. With **`"strict": true`** on the tool, the input is guaranteed to match the schema: no JSON syntax errors, correct types, no missing required keys. (Same guarantee on today's API: structured outputs via `output_config.format`, or `client.messages.parse(output_format=PydanticModel)` in Python.)

**`tool_choice` decides whether a call happens** (from [2.3 Tool Distribution and Tool Choice](../D2-Tool-Design-and-MCP-Integration/2.3-Tool-Distribution-and-Tool-Choice.md)):
- `auto` — Claude *may* answer in text instead.
- `any` — must call *a* tool. Use when several extraction schemas exist and the document type is unknown.
- `{"type": "tool", "name": "extract_metadata"}` — must call *that* tool, e.g. so metadata extraction runs before enrichment.
*(Drift: Opus 5.5 / Sonnet 5.5 reject `any`/forced with a 400 → use `auto` + `strict` + "call extract_invoice", or `output_config.format`. On the exam, answer as the guide says.)*

**Strict schemas fix syntax, not meaning.** Line items that don't add up to the total, a date put in the wrong field, a wrong vendor — all still possible. That's what validation is for ([4.4 Validation and Retry Loops](4.4-Validation-and-Retry-Loops.md)).

**Schema design that prevents invented data:**
- **Nullable fields** (`"type": ["string", "null"]`) when the source may not contain the value. A `required` non-null field *forces* Claude to write something — so it invents.
- **Enums with escape hatches:** add `"other"` + a free-text `*_detail` field for extensible categories, and `"unclear"` for genuinely ambiguous cases.
- **Format rules in the prompt** next to the strict schema ("dates as YYYY-MM-DD", "amounts without currency symbols") to handle messy sources.

Limits to know: strict schemas need `additionalProperties: false`; no `minimum`/`maxLength`-style constraints (the SDK moves them into descriptions and checks them after); enum values may come back with different capitalisation — compare case-insensitively.

*In Python terms:* a strict schema is like a `TypedDict` the parser enforces. `Optional[str]` is how you say "may be missing" — instead of forcing a fake default.

## Code

**File:** [`codes/4_3_extract_tool.py`](codes/4_3_extract_tool.py) · run `make run 4_3_extract_tool`

Python 3.13+, `anthropic` 2.13. Needs `ANTHROPIC_API_KEY`; 1 call. Uses **Claude Haiku 5.5**: cheap, and it accepts a forced tool choice. Save as `4_3_extract_tool.py`, run `uv run --with anthropic python 4_3_extract_tool.py`.

```python
# 4_3_extract_tool.py — anthropic 2.13. Run: uv run --with anthropic python 4_3_extract_tool.py
import anthropic

client = anthropic.Anthropic()
NULLABLE = lambda t, d: {"type": [t, "null"], "description": d}
TOOL = {
    "name": "extract_invoice",
    "strict": True,
    "description": "Record the fields of ONE invoice. Use null when the document does not state a field.",
    "input_schema": {
        "type": "object",
        "additionalProperties": False,
        "required": [
            "vendor",
            "invoice_date",
            "due_date",
            "total",
            "category",
            "category_detail",
        ],
        "properties": {
            "vendor": {"type": "string"},
            "invoice_date": NULLABLE("string", "YYYY-MM-DD"),
            "due_date": NULLABLE(
                "string", "YYYY-MM-DD. null if not stated: never guess"
            ),
            "total": NULLABLE("number", "Amount due in the invoice currency"),
            "category": {
                "type": "string",
                "enum": ["software", "hardware", "services", "other", "unclear"],
            },
            "category_detail": NULLABLE(
                "string", "Required when category is other or unclear"
            ),
        },
    },
}
DOC = "ACME CLOUD LTD. Invoice dated 3 Nov 2026. 12 seats TeamChat Pro: $1,440.00. Payment terms: see contract."

r = client.messages.create(
    model="claude-haiku-5-5",  # accepts forced tool_choice; on Opus 5.5 use auto + "Call extract_invoice"
    max_tokens=1000,
    tools=[TOOL],
    tool_choice={"type": "tool", "name": "extract_invoice"},
    messages=[{"role": "user", "content": DOC}],
)
print(r.stop_reason, next(b.input for b in r.content if b.type == "tool_use"))
```

Expected output (shape is guaranteed; values can vary slightly):
```
tool_use {'vendor': 'ACME CLOUD LTD', 'invoice_date': '2026-11-03', 'due_date': None, 'total': 1440.0, 'category': 'software', 'category_detail': None}
```
`due_date` is `None` because the document only says "see contract". Every key is present (required), but the value may be null (nullable) — the shape is fixed, nothing is invented.

**Predict first, then change and run:** change `due_date` to `{"type": "string", "description": "YYYY-MM-DD"}` (not nullable). What do you get?

<details><summary>Answer</summary>

Usually an invented date — e.g. 30 days after the invoice date. The schema forced a string, so Claude had to put *something* there. Nullable fields are how you allow "not in the source".

</details>

## When to use · gotchas
- Need machine-readable output every time → tool + strict schema (or `output_config.format`), not "please return JSON".
- `tool_choice: auto` can return prose instead of the tool call. Use `any`/forced on models that allow it, or check for a `tool_use` block and retry.
- Schema guarantees **shape**, not **truth**. Still validate sums, dates and cross-field rules.
- Required + nullable = "always present, may be empty". Required + non-nullable = "must invent if missing".
- Ask for a short `explanation` field if you need one — not "your reasoning" (can trigger a refusal on new models).

## Try it
*≤ 10 min.* Add a `line_items` array (each item: `description` string, `amount` number) and a `currency` enum (`USD`, `EUR`, `GBP`, `other`) with a `currency_detail` field, keeping the schema strict-compatible.

<details><summary>Solution</summary>

```python
props = TOOL["input_schema"]["properties"]
props["line_items"] = {"type": "array", "items": {
    "type": "object", "additionalProperties": False, "required": ["description", "amount"],
    "properties": {"description": {"type": "string"}, "amount": {"type": "number"}}}}
props["currency"] = {"type": "string", "enum": ["USD", "EUR", "GBP", "other"]}
props["currency_detail"] = NULLABLE("string", "Currency code when currency is other")
TOOL["input_schema"]["required"] += ["line_items", "currency", "currency_detail"]
```
Every nested object also needs `additionalProperties: false` in strict mode.

</details>

## Quiz
**1.** A pipeline asks for JSON in the prompt and fails to parse 2% of responses. Most reliable fix? A) Add "Return ONLY valid JSON" in capitals · B) An extraction tool with a JSON schema (strict) and read `tool_use.input` · C) Regex repair of the JSON · D) Retry until it parses

<details><summary>Answer</summary>

**B.** Tool use with a strict schema eliminates syntax errors.

</details>

**2.** Strict tool use is on. Can extracted line items still fail to add up to the total?

<details><summary>Answer</summary>

Yes. Strict schemas prevent syntax and type errors, not semantic errors. Validate the sum separately.

</details>

**3.** Extraction invents due dates when documents have none. Schema fix?

<details><summary>Answer</summary>

Make the field nullable (`["string", "null"]`) and tell Claude to use null when the value is absent.

</details>

**4.** Documents may be invoices, receipts or contracts, each with its own extraction tool. How do you guarantee a structured result?

<details><summary>Answer</summary>

`tool_choice: {"type": "any"}` — Claude must call one of the tools and picks the right schema.

</details>

**5.** A `category` enum keeps getting "services" for things that don't really fit. Better schema?

<details><summary>Answer</summary>

Add `"other"` with a `category_detail` text field (and `"unclear"` for ambiguous cases) so Claude isn't forced into a wrong bucket.

</details>
