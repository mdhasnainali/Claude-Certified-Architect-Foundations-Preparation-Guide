# 4.5 Batch Processing

## Goal
After this you can decide when the Message Batches API fits, size submission windows for an SLA, and handle batch failures by `custom_id`. *(Task statement 4.5)*

## Guess first
1. Batches cost 50% less. Should a pre-merge check that developers wait for use them?
2. You submit 1,000 requests. Do results come back in the same order?

## Idea
**Message Batches API — the facts the exam uses:**
- **50% cheaper** than normal calls.
- Processed asynchronously: most batches end within **1 hour**, but the limit is **24 hours** and there is **no latency SLA**.
- Up to 100,000 requests or 256 MB per batch; results downloadable for 29 days.
- Each request has a **`custom_id`**. Results come back in **any order** — match them by `custom_id`, never by position.
- One failed request doesn't affect the others.
- A request runs **one turn**: it can't stop to run *your* tools and continue in the same request. (Server tools like web search run inside; a client `tool_use` just ends that result.) So no multi-turn client tool loops inside a batch request.

**Match the API to the wait:**
| Workload | API |
|---|---|
| Pre-merge check, a user waiting, anything blocking | **Synchronous** Messages API |
| Overnight reports, weekly audits, nightly test generation, backfills | **Batches** |
(Official sample question 11: batch the overnight tech-debt report, keep the pre-merge check real-time.)

**Submission frequency for an SLA.** A document that arrives just after a submission waits a whole window, then up to 24 h of processing. Worst case = window + 24 h. For a 30-hour SLA the window must be under 6 h; the guide's example uses **4-hour windows** to keep a margin.

**Handling failures.** Resubmit **only the failed `custom_id`s**, with a fix where needed — for example, split a document that was too long for the context window into chunks.

**Refine before you scale.** Test and fix the prompt on a small sample first. A 2% failure rate on 100,000 documents is 2,000 resubmissions.

*In Python terms:* like `concurrent.futures.as_completed()` — results come back as they finish, so you key them by an ID, not by list position.

**Part A — SLA math.** Python 3.13+, offline. Save as `4_5_sla.py`, run `python3 4_5_sla.py`.

```python
# 4_5_sla.py — Python 3.13+, offline. How often must you submit batches to meet a 30-hour SLA?
SLA_HOURS = 30  # promise to the business
BATCH_MAX_HOURS = 24  # worst-case batch processing time

for window_hours in (2, 4, 6, 8):
    # a document arriving just after a submission waits a full window
    worst_case_hours = window_hours + BATCH_MAX_HOURS
    if worst_case_hours < SLA_HOURS:
        status = "OK"
    elif worst_case_hours == SLA_HOURS:
        status = "no margin"
    else:
        status = "MISSES SLA"
    print(f"submit every {window_hours} h → worst case {worst_case_hours} h → {status}")
```

Expected output:
```
submit every 2 h → worst case 26 h → OK
submit every 4 h → worst case 28 h → OK
submit every 6 h → worst case 30 h → no margin
submit every 8 h → worst case 32 h → MISSES SLA
```

**Part B — a real batch.** `anthropic` 2.13, needs `ANTHROPIC_API_KEY` (3 tiny requests at half price). It can take minutes, up to 24 h. Save as `4_5_batch_run.py`, run `uv run --with anthropic python 4_5_batch_run.py`.

```python
# 4_5_batch_run.py — anthropic 2.13. Run: uv run --with anthropic python 4_5_batch_run.py  (takes minutes, up to 24 h)
import time
import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()
INVOICES = {
    "inv-001": "Invoice A. Hosting $120. Total $120.",
    "inv-002": "Invoice B. Support $80. Total $80.",
    "inv-003": "Invoice C. Licences $1,440. Total $1,440.",
}

def build_request(doc_id: str, text: str) -> Request:
    return Request(
        custom_id=doc_id,
        params=MessageCreateParamsNonStreaming(
            model="claude-haiku-5-5",
            max_tokens=1000,
            messages=[
                {
                    "role": "user",
                    "content": f"Reply with the invoice total as a plain number.\n{text}",
                }
            ],
        ),
    )

batch = client.messages.batches.create(
    requests=[build_request(doc_id, text) for doc_id, text in INVOICES.items()]
)
while (
    batch := client.messages.batches.retrieve(batch.id)
).processing_status != "ended":
    time.sleep(60)  # most batches end within 1 hour; the hard limit is 24 hours

failed_ids = []
# results arrive in ANY order → match them by custom_id
for entry in client.messages.batches.results(batch.id):
    if entry.result.type == "succeeded":
        print(
            entry.custom_id,
            "→",
            next(
                block.text
                for block in entry.result.message.content
                if block.type == "text"
            ),
        )
    else:
        failed_ids.append(entry.custom_id)  # errored / expired / canceled
print("resubmit only these:", failed_ids)
```

Expected output (order may differ):
```
inv-002 → 80
inv-001 → 120
inv-003 → 1440
resubmit only these: []
```

**Predict first, then check:** in Part A, the business shortens the SLA to 26 hours. Which windows still work?

<details><summary>Answer</summary>

Only windows under 2 hours (2 h gives exactly 26 h — no margin). Batch processing alone can take 24 h, so a tight SLA leaves almost no room — consider the synchronous API for that workload.

</details>

## When to use · gotchas
- Never batch a workflow someone is waiting on. "Usually faster than 24 h" is not a guarantee.
- Don't "batch with a timeout fallback to real time" when the simple answer is: right API for each workload.
- Always set meaningful `custom_id`s (document IDs), unique per batch.
- Resubmit failures selectively; fix the cause (chunk oversized documents) before resubmitting.
- Prompt caching works with batches; long shared prefixes save more.

## Try it
*≤ 10 min.* `inv-003` failed because the document was too long. Write `resubmit(failed_ids, INVOICES)` that splits each failed document into two halves with `custom_id`s like `inv-003#1` and `inv-003#2`, and returns the new `Request` list.

<details><summary>Solution</summary>

```python
def resubmit(failed_ids: list[str], invoices: dict[str, str]) -> list[Request]:
    requests = []
    for doc_id in failed_ids:
        text = invoices[doc_id]
        half = len(text) // 2
        for part, chunk in enumerate((text[:half], text[half:]), start=1):
            requests.append(build_request(f"{doc_id}#{part}", chunk))
    return requests

print([request["custom_id"] for request in resubmit(["inv-003"], INVOICES)])   # ['inv-003#1', 'inv-003#2']
```
In real code, split at a page or section boundary, not in the middle of a line, and merge the parts' results afterwards.

</details>

## Quiz
**1.** Two workflows: a blocking pre-merge check and an overnight tech-debt report. The manager wants both on batches for 50% savings. Best answer? A) Batch only the overnight report; keep the pre-merge check synchronous · B) Batch both with status polling · C) Keep both synchronous · D) Batch both with a real-time fallback on timeout

<details><summary>Answer</summary>

**A.** Batches have no latency SLA (up to 24 h). D adds complexity when matching each workload to the right API is simpler.

</details>

**2.** How do you match batch results to input documents?

<details><summary>Answer</summary>

By `custom_id` — results come back in any order.

</details>

**3.** SLA: results within 30 h of a document arriving. Batches can take 24 h. How often do you submit?

<details><summary>Answer</summary>

At most every 6 h; e.g. every 4 h to keep a safety margin (worst case 4 + 24 = 28 h).

</details>

**4.** 3% of a 50,000-document batch failed (some exceeded the context window). What do you do?

<details><summary>Answer</summary>

Resubmit only the failed `custom_id`s, with fixes such as chunking the oversized documents.

</details>

**5.** An extraction flow needs Claude to call your `lookup_vendor` tool and continue with its result. Can one batch request do that?

<details><summary>Answer</summary>

No — a batch request can't run your client tool and resume mid-request. Use the synchronous API for that loop (or split it into separate requests/batches).

</details>
