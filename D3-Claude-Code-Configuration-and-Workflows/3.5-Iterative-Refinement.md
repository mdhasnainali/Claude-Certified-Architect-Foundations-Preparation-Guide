# 3.5 Iterative Refinement

## Goal
After this you can steer Claude Code to the right result faster: input/output examples, tests first, the interview pattern, and knowing when to send all issues at once. *(Task statement 3.5)*

## Guess first
1. You described a text transformation in two paragraphs; Claude got it half right twice. What is the fastest way to make the rule clear?
2. Three bugs: a wrong date parse, a wrong currency symbol, and a timeout. Send them one by one, or all in one message?

## Idea
**1. Concrete input → output examples.** When prose gets interpreted differently each time, give 2–3 examples: `"  Café crème " → "cafe-creme"`. Examples remove ambiguity that words can't (same idea as few-shot in [4.2 Few-Shot Examples](../D4-Prompt-Engineering-and-Structured-Output/4.2-Few-Shot-Examples.md)).

**2. Test-driven iteration.** Write the tests **first** — expected behaviour, edge cases, performance needs. Then let Claude implement, run the tests, and **share the exact failures** back. A pass/fail check lets Claude close the loop itself (Anthropic: "Give Claude something it can run that comes back pass or fail"). For an edge case (e.g. null values in a migration script), add a specific test case with the input and the expected output.

**3. The interview pattern.** In an unfamiliar area, before any code, ask Claude to **interview you**: it asks about things you didn't think of (cache invalidation, failure modes, limits). Anthropic's example: *"Interview me until you could write the spec, then write it to SPEC.md."* Then build from the spec in a fresh session.

**4. All at once vs one by one:**
- Issues that **interact** (fixing one changes the others — e.g. a shared date parser behind two bugs) → describe them **together in one detailed message**.
- **Independent** issues → fix them **one after another**, each verified before the next.

**5. Be specific.** Name the file, the symptom, and what "fixed" means: not "fix the login bug" but "login fails after session timeout; look at token refresh in `src/auth/`; write a failing test first, then fix".

*In Python terms:* it's TDD with a very fast pair programmer: red (failing test) → green (Claude's change) → you paste the red lines back until everything is green.

## Code

**File:** [`codes/3_5_tdd_slug.py`](codes/3_5_tdd_slug.py) · run `make run 3_5_tdd_slug`

Python 3.13+, offline. This is the "tests first" half: concrete examples as a test table, plus an output you can paste straight back to Claude. Save as `3_5_tdd_slug.py`, run `python3 3_5_tdd_slug.py`.

```python
# 3_5_tdd_slug.py — Python 3.13+, offline. Tests first: concrete input → output examples Claude must satisfy.
import re

TEST_CASES = [  # (input, expected) — written BEFORE the implementation
    ("Hello World", "hello-world"),
    ("  Café crème  ", "cafe-creme"),
    ("C++ & Rust: 2026!", "c-rust-2026"),
    ("already-a-slug", "already-a-slug"),
    ("", ""),
]

def slugify(text: str) -> str:  # first attempt (pretend Claude wrote it)
    text = text.strip().lower()
    return re.sub(r"[^a-z0-9]+", "-", text).strip("-")

failures = [
    (text, expected, actual)
    for text, expected in TEST_CASES
    if (actual := slugify(text)) != expected
]
print(f"{len(TEST_CASES) - len(failures)}/{len(TEST_CASES)} passing")
for text, expected, actual in failures:  # paste exactly this back to Claude
    print(f"FAIL slugify({text!r}) → {actual!r}, expected {expected!r}")
```

Expected output:
```
4/5 passing
FAIL slugify('  Café crème  ') → 'caf-cr-me', expected 'cafe-creme'
```
In Claude Code you would say: *"Make all TEST_CASES pass. Current failure: `slugify('  Café crème  ') → 'caf-cr-me', expected 'cafe-creme'`."* — precise, testable, no prose rule needed.

The interview pattern, to paste into Claude Code before a feature in unfamiliar territory:
```text
I want to add caching to our product-price API but haven't thought it through.
Interview me, one question at a time, until you could write the spec: what to cache,
invalidation, TTLs, failure modes, metrics. Then write it to SPEC.md. Don't write code yet.
```

**Predict first, then change and run:** fix `slugify` yourself so all 5 pass. Hint: accents need converting before the regex.

<details><summary>Answer</summary>

```python
import unicodedata
def slugify(text: str) -> str:
    text = unicodedata.normalize("NFKD", text).encode("ascii", "ignore").decode()
    return re.sub(r"[^a-z0-9]+", "-", text.strip().lower()).strip("-")
```
Output: `5/5 passing`.

</details>

## When to use · gotchas
- Prose keeps being misread → switch to 2–3 input/output examples.
- Behaviour that matters → tests before code; paste the **exact** failing output, not "it still doesn't work".
- Unfamiliar domain → interview first, then a spec, then code in a fresh session.
- Interacting bugs → one message with all of them; independent bugs → one at a time.
- "Think step by step" / "be thorough" are just words; effort level and a runnable check matter more.

## Quiz
**1.** Claude keeps misreading your prose description of a data transformation. Most effective next step? A) Write a longer description · B) Give 2–3 concrete input/output examples · C) Switch to plan mode · D) Ask Claude to think harder

<details><summary>Answer</summary>

**B.** Concrete examples communicate the expected transformation where prose fails.

</details>

**2.** Describe test-driven iteration with Claude Code.

<details><summary>Answer</summary>

Write tests (expected behaviour, edge cases, performance) first; let Claude implement; share the specific test failures; repeat until all pass.

</details>

**3.** You're adding a feature in a domain you don't know well. What pattern surfaces the design questions you'd miss?

<details><summary>Answer</summary>

The interview pattern: have Claude ask you questions (e.g. cache invalidation, failure modes) before implementing.

</details>

**4.** Three independent bugs in different modules. One message or sequential?

<details><summary>Answer</summary>

Sequential — fix and verify each independently. (Interacting bugs go in one detailed message.)

</details>

**5.** A migration script mishandles null values. How do you get a reliable fix?

<details><summary>Answer</summary>

Give a specific test case: an example input with nulls and the expected output, then iterate on the failure.

</details>
