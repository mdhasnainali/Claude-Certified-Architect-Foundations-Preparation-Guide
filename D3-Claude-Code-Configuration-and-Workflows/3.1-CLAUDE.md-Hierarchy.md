# 3.1 CLAUDE.md Hierarchy

## Goal
After this you can put each instruction at the right CLAUDE.md level, keep big instruction sets modular with `@import` and `.claude/rules/`, and debug "why doesn't Claude follow this?" with `/memory`. *(Task statement 3.1)*

## Guess first
1. You wrote the team's coding standards in `~/.claude/CLAUDE.md`. A new teammate clones the repo. Does Claude follow the standards for them?
2. Root `CLAUDE.md` says one thing, `packages/api/CLAUDE.md` says more. Does the second file replace the first?

## Idea
**The levels** (load order, broadest first):

| Level | File | Who gets it |
|---|---|---|
| Managed policy | `/etc/claude-code/CLAUDE.md` (Linux) | Everyone in the organisation |
| **User** | `~/.claude/CLAUDE.md` (+ `~/.claude/rules/`) | **Only you**, all projects — not shared through git |
| **Project** | `./CLAUDE.md` or `./.claude/CLAUDE.md` (+ `.claude/rules/`) | Everyone who clones the repo |
| Local | `./CLAUDE.local.md` (gitignored) | Only you, this project |
| **Directory** | `packages/api/CLAUDE.md` | Loads when Claude works on files in that folder |

Files are **added together**, not overridden; more specific ones come later in context. Files above the working directory load at start; subdirectory files load on demand.

**The classic bug** (exam): "a new team member doesn't get the instructions" → they live in **user-level** `~/.claude/CLAUDE.md`, which is never shared. Move them to the project CLAUDE.md.

**Keep it modular:**
- **`@import`**: `@docs/standards/api-conventions.md` inside a CLAUDE.md pulls that file in (path relative to the importing file). Each package's CLAUDE.md imports only the standards its maintainers say apply.
- **`.claude/rules/`**: split a huge CLAUDE.md into topic files — `testing.md`, `api-conventions.md`, `deployment.md`. Rules without `paths:` load every session like CLAUDE.md; rules *with* `paths:` load only for matching files ([3.3 Path-Specific Rules](3.3-Path-Specific-Rules.md)).

**Debug with `/memory`.** It lists the memory files (user, project, local) for this session and opens them for editing. Use it when Claude behaves differently across sessions or people: first check *which* files are in play.

**A typical setup:** `~/.claude/CLAUDE.md` holds your personal tool rules; the repo's `CLAUDE.md` is the project level; `.claude/rules/testing.md` is a project rule without `paths:`; `~/.claude/rules/` holds user-level rules that apply in every project.

*In Python terms:* like config layering — defaults, then a user config, then a project config, merged in order. Except CLAUDE.md files are concatenated text, not key-by-key overrides.

## Code

**File:** [`codes/3_1_setup.sh`](codes/3_1_setup.sh)

Bash + Claude Code 2.1.x. The script is offline; the checks run in Claude Code with your normal login. Save as `3_1_setup.sh` in a scratch folder, run `bash 3_1_setup.sh`.

```bash
#!/usr/bin/env bash
# 3_1_setup.sh — builds a demo repo to see CLAUDE.md layers. Run: bash 3_1_setup.sh
set -euo pipefail
mkdir -p claude-demo/{.claude/rules,docs/standards,packages/api,packages/web} && cd claude-demo && git init -q
cat > CLAUDE.md <<'MD'
# Team instructions (project level — shared via git)
- Run tests with `make test`. Python 3.14, uv for packages.
- Never commit secrets.
MD
cat > packages/api/CLAUDE.md <<'MD'
# API package (directory level — loads when Claude works in packages/api/)
@../../docs/standards/api-conventions.md
MD
cat > docs/standards/api-conventions.md <<'MD'
- Every endpoint validates input with Pydantic and returns errors as {"error": {...}}.
MD
cat > .claude/rules/testing.md <<'MD'
# Testing (rule without paths: loads every session, like CLAUDE.md)
- Tests use pytest fixtures from tests/conftest.py. No network in unit tests.
MD
echo "- I like short answers." > CLAUDE.local.md && echo "CLAUDE.local.md" > .gitignore
find . -name '*.md' -not -path './.git/*' | sort
```

Expected output:
```
./CLAUDE.local.md
./CLAUDE.md
./.claude/rules/testing.md
./docs/standards/api-conventions.md
./packages/api/CLAUDE.md
```

Then: `cd claude-demo && claude`, and try:
1. `/memory` → you see the user, project and local memory files listed.
2. "Create packages/api/users.py with a GET /users endpoint." → it should follow the imported API conventions (validation + error shape).
3. "Which of my instructions came from a file only I have?" → `CLAUDE.local.md` (and your `~/.claude/CLAUDE.md`).

**Predict first, then check:** move the line "Never commit secrets." from `CLAUDE.md` into your `~/.claude/CLAUDE.md`. Who still gets it?

<details><summary>Answer</summary>

Only you — in every project. Teammates lose it, because user-level files are not in the repo. That's exactly the "new teammate doesn't get the instructions" bug. (Undo the move afterwards.)

</details>

## When to use · gotchas
- Team standards → **project** CLAUDE.md or `.claude/rules/` (committed). Personal taste → `~/.claude/CLAUDE.md` or `CLAUDE.local.md`.
- A 500-line CLAUDE.md wastes context every turn. Split into rules; move task-specific procedures into skills (3.2).
- `@import` paths are relative to the file that contains them. Paths outside the project need a one-time approval.
- Everything in always-loaded files costs tokens on every request — keep it to rules that apply almost always.

## Try it
*≤ 10 min.* In `claude-demo`, the web team wants its own React standards, and the API team must not see them. Set it up with one new standards file and one import.

<details><summary>Solution</summary>

```bash
cat > docs/standards/react.md <<'MD'
- Function components with hooks only. Props typed with TypeScript interfaces.
MD
printf '# Web package\n@../../docs/standards/react.md\n' > packages/web/CLAUDE.md
```
The import lives in `packages/web/CLAUDE.md`, so it loads only when Claude works in `packages/web/`.

</details>

## Quiz
**1.** A new developer says Claude ignores the team's naming rules. Everyone else is fine. The rules are in the tech lead's `~/.claude/CLAUDE.md`. Fix? A) Ask the developer to copy the file · B) Move the rules into the project CLAUDE.md (or `.claude/rules/`) in the repo · C) Put them in `CLAUDE.local.md` · D) Restart Claude Code

<details><summary>Answer</summary>

**B.** User-level files apply only to their owner and aren't shared through version control.

</details>

**2.** Root `CLAUDE.md` and `services/billing/CLAUDE.md` both exist. Claude works in `services/billing/`. What does it see?

<details><summary>Answer</summary>

Both — they're concatenated; the more specific file comes later in context.

</details>

**3.** Each package should load only the standards files that apply to it. Which feature?

<details><summary>Answer</summary>

`@import` in each package's CLAUDE.md, pointing at the relevant standards files.

</details>

**4.** The project CLAUDE.md is 600 lines covering testing, API, deployment and security. Better structure?

<details><summary>Answer</summary>

Split it into topic files in `.claude/rules/` (e.g. `testing.md`, `api-conventions.md`, `deployment.md`).

</details>

**5.** Claude behaves differently in two sessions of the same project. First debugging step?

<details><summary>Answer</summary>

Run `/memory` to see which memory files are in play (user, project, local) and check them.

</details>
