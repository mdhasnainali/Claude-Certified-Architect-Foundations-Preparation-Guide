# 3.4 Plan Mode vs Direct Execution

## Goal
After this you can decide between plan mode and direct execution for a task, and combine them — plan the big change, then execute it. *(Task statement 3.4)*

## Guess first
1. "Split our monolith into microservices." Start editing right away and let the boundaries emerge, or plan first?
2. "Add a check that rejects dates before 1900 in `parse_date()`, with one test." Plan mode or straight to work?

## Idea
**Plan mode** = Claude researches and proposes, but does **not** edit your source. It reads files, runs exploring commands, and writes a plan you approve (or edit) before any change.

**Use plan mode when the task has:**
- large-scale changes across many files (a library migration touching 45+ files),
- several valid approaches to choose between (two integration options with different infrastructure needs),
- architectural decisions (service boundaries, module dependencies),
- multi-file changes where a wrong start means costly rework.

**Use direct execution when the change is simple and well-scoped:** a single-file bug fix with a clear stack trace, one validation check in one function, a date-format conditional.

**Combine them:** plan the library migration in plan mode, approve the plan, then execute it directly. Approving a plan switches the session into an editing mode.

**The Explore subagent** keeps verbose discovery out of your main conversation: it searches read-only in its own context and returns a summary. Use it for the discovery phase of multi-phase tasks so your context isn't exhausted before the real work starts ([5.4 Context in Codebase Exploration](../D5-Context-Management-and-Reliability/5.4-Context-in-Codebase-Exploration.md)).

**Official sample question 5** (monolith → microservices): plan mode. Wrong options: start editing and "let boundaries emerge" (late surprises, rework), direct execution with detailed upfront instructions (assumes you already know the structure), "switch to plan mode only if complexity appears" (the complexity is already stated in the task).

**How to enter plan mode:** `Shift+Tab` in a session, prefix one prompt with `/plan`, or start with `claude --permission-mode plan`. At the approval prompt you can approve, keep planning, or press `Ctrl+G` to edit the plan.

*In Python terms:* plan mode is like writing the design doc / RFC before the refactor PR. For a one-line fix you just open the PR.

## Code
Claude Code 2.1.x, your normal login. Use any real repo you have (or `claude-demo/`).

```bash
# 1) Big change → plan first
claude --permission-mode plan
#   > Migrate every HTTP call in this repo from requests to httpx (sync client).
#   > Use the Explore agent to find all call sites first, then propose a plan:
#   > order of files, risks (timeouts, sessions, retries), and the tests to run.
#   → read the plan · Ctrl+G to edit it · approve → Claude starts editing

# 2) Small, clear change → direct execution
claude "In utils/dates.py, make parse_date() reject years before 1900 with ValueError. Add one test."

# 3) In one session: /plan for the risky part, then plain prompts for the rest
#   > /plan How should we split billing.py (1,800 lines) into modules?
```
Expected: in (1) Claude explores and returns a plan, and **no files change** until you approve. In (2) Claude edits and adds the test right away.

**Predict first, then check:** in (1), before approving, run `git status` in another terminal. What do you see?

<details><summary>Answer</summary>

No changes to your source files — plan mode doesn't edit until you approve. (Claude may write the plan file itself, but not your code.)

</details>

## When to use · gotchas
- "Multiple valid approaches", "architectural", "dozens of files", "unfamiliar codebase" → plan mode.
- "Single file", "clear stack trace", "one check", "well understood" → direct execution.
- Don't plan trivial edits — it costs time and context for nothing.
- Don't "start direct and switch to plan if it gets complex" when the task *already* says it is complex.
- Long discovery → Explore subagent, so the plan phase doesn't fill your context.

## Try it
*≤ 10 min.* Plan mode or direct execution? Decide for each, with one reason.
(a) Fix a `KeyError` at `orders.py:88` from a stack trace · (b) Add OAuth login, choosing between Auth0 and your own server · (c) Rename one private helper used in one file · (d) Move 60 files from `utils/` into domain packages · (e) Upgrade Django 3 → 5.

<details><summary>Solution</summary>

(a) Direct — one file, clear cause. (b) Plan — two valid approaches with different infrastructure. (c) Direct — tiny and scoped. (d) Plan — many files, import paths, architecture. (e) Plan — large migration with breaking changes; explore first, then execute the approved plan.

</details>

## Quiz
**1.** Restructure a monolith into microservices: dozens of files, decisions on service boundaries. Which approach? A) Plan mode to explore and design first · B) Direct execution, let boundaries emerge · C) Direct execution with detailed upfront instructions · D) Direct, switch to plan mode if it gets complex

<details><summary>Answer</summary>

**A.** Large-scale, architectural, multiple valid approaches.

</details>

**2.** A single-file bug fix with a clear stack trace. Mode?

<details><summary>Answer</summary>

Direct execution.

</details>

**3.** During a multi-phase task, discovery output fills the context. What helps?

<details><summary>Answer</summary>

Use the Explore subagent for the discovery phase; it returns a summary and keeps the verbose output out of the main conversation.

</details>

**4.** How do you combine plan mode and direct execution for a library migration?

<details><summary>Answer</summary>

Plan mode to investigate and produce the migration plan; approve it; then execute the planned approach.

</details>

**5.** Name three ways to enter plan mode.

<details><summary>Answer</summary>

`Shift+Tab` in a session, `/plan` before a prompt, `claude --permission-mode plan`.

</details>
