# 3.2 Commands and Skills

## Goal
After this you can put slash commands and skills at the right scope, configure skill frontmatter (`context: fork`, `allowed-tools`, `argument-hint`), and choose between a skill and CLAUDE.md. *(Task statement 3.2)*

## Guess first
1. You want a `/review` command that every developer gets after cloning. Where do you put the file?
2. A skill that maps the whole codebase prints 3,000 lines of output into your chat. How can it keep your main conversation clean?

## Idea
**Scope = location** (same idea as 3.1):

| | Shared with team (in git) | Personal (only you) |
|---|---|---|
| Commands | `.claude/commands/review.md` → `/review` | `~/.claude/commands/` |
| Skills | `.claude/skills/<name>/SKILL.md` | `~/.claude/skills/<name>/SKILL.md` |

Official sample question 4: a team `/review` command goes in the **project's `.claude/commands/`**. Not `~/.claude/commands/` (personal), not CLAUDE.md (instructions, not commands), and there is no `.claude/config.json` commands array.

**Skill frontmatter the exam names:**
- **`context: fork`** — runs the skill in an **isolated subagent**. Its verbose output (codebase analysis) or exploratory work (brainstorming alternatives) stays out of the main conversation; you get the result. (`agent:` picks the subagent type, e.g. `Explore`.)
- **`allowed-tools`** — the tools the skill may use while running. Exam framing: *restrict* a skill's tools, e.g. only file writes, so it can't do destructive things.
- **`argument-hint`** — shown in autocomplete (e.g. `[issue-number]`) so a developer knows which argument the skill expects; `$ARGUMENTS` receives it.

**Personal variants:** want your own version of a team skill? Create it in `~/.claude/skills/` **with a different name** (e.g. `review-strict`). A personal skill with the *same* name would silently replace the team's for you — confusing, and teammates' results differ from yours.

**Skill or CLAUDE.md?**
- **CLAUDE.md / rules** = always loaded → universal standards ("use uv", "never commit secrets").
- **Skills** = loaded on demand → task-specific workflows (deploy, release notes, codebase map). Only the short description sits in context until used.

> [!WARNING]
> **Exam vs today's Claude Code**
> - Custom **commands have been merged into skills**. `.claude/commands/*.md` still works; a skill folder adds supporting files. Same `/name` either way.
> - Today `allowed-tools` **pre-approves** the listed tools during the skill's turn; it doesn't remove others. To *remove* tools, current docs use `disallowed-tools`. On the exam, read `allowed-tools` as "restrict the skill's tools".

*In Python terms:* CLAUDE.md is like module-level constants imported everywhere; a skill is a function you call only when needed — and `context: fork` runs it in a subprocess so its prints don't flood your terminal.

## Code

**File:** [`codes/3_2_setup.sh`](codes/3_2_setup.sh)

Bash + Claude Code 2.1.x. Run inside `claude-demo/` from [3.1 CLAUDE.md Hierarchy](3.1-CLAUDE.md-Hierarchy.md): save as `3_2_setup.sh`, run `bash 3_2_setup.sh`.

```bash
#!/usr/bin/env bash
# 3_2_setup.sh — run inside claude-demo/ (from lesson 3.1). Adds one command and one skill.
set -euo pipefail
mkdir -p .claude/commands .claude/skills/codebase-map
cat > .claude/commands/review.md <<'MD'
---
description: Run the team review checklist on the current branch
argument-hint: [base-branch]
---
Review `git diff $ARGUMENTS...HEAD` (use main if no branch was given) against our checklist:
bugs, missing tests, security. Skip style. Output: file:line · issue · severity · fix.
MD
cat > .claude/skills/codebase-map/SKILL.md <<'MD'
---
name: codebase-map
description: Map an unfamiliar codebase (modules, entry points, where tests live) and return a short summary. Use before large changes.
argument-hint: [folder]
context: fork
agent: Explore
allowed-tools: Read Grep Glob
disallowed-tools: Edit Write
---
Map the code under $ARGUMENTS (the whole repo if empty):
1. Top-level modules, one line each.  2. Entry points.  3. Where tests live.
Return at most 15 lines. Do not change any file.
MD
find .claude -type f | sort
```

Expected output:
```
.claude/commands/review.md
.claude/rules/testing.md
.claude/skills/codebase-map/SKILL.md
```
Then start `claude` and type `/` → `/review [base-branch]` and `/codebase-map [folder]` appear with their hints. Run `/codebase-map packages` → a separate subagent explores; only its ≤15-line summary lands in your chat.

A typical team repo: `/review`, `/deploy-check` and a few more are project skills in `.claude/skills/`, each with a `description` that tells Claude when to use it.

**Predict first, then check:** remove `context: fork` and `agent: Explore` from the skill and run it again on a big repo. What changes in your main conversation?

<details><summary>Answer</summary>

All the exploration (file reads, searches) now happens in your main context, so the conversation fills with discovery output. `context: fork` is what isolates it.

</details>

## When to use · gotchas
- Team workflow → project `.claude/commands/` or `.claude/skills/` (committed). Personal → `~/.claude/…`, with a **different name** from team skills.
- Verbose or exploratory skills → `context: fork`.
- Skills that must not touch files → limit their tools (exam: `allowed-tools`; today: `disallowed-tools` / a read-only agent).
- Put the key use case first in `description` — that is what Claude reads to decide when to use the skill.
- `context: fork` needs an actual task in the skill; a skill with only "conventions" gives the subagent nothing to do.

## Try it
*≤ 10 min.* Create a personal variant of `/review` that also checks performance, without affecting teammates.

<details><summary>Solution</summary>

```bash
mkdir -p ~/.claude/commands
cat > ~/.claude/commands/review-perf.md <<'MD'
---
description: My review — team checklist plus performance (N+1 queries, O(n²) loops)
argument-hint: [base-branch]
---
Do the same checks as /review on `git diff $ARGUMENTS...HEAD`, then add a
"Performance" section: N+1 queries, nested loops over large data, missing indexes.
MD
```
A different name (`/review-perf`) keeps the team's `/review` unchanged for everyone, including you.

</details>

## Quiz
**1.** A `/deploy-check` command must be available to every developer after `git pull`. Where? A) `~/.claude/commands/` · B) `.claude/commands/` in the repo · C) The project CLAUDE.md · D) `.claude/config.json`

<details><summary>Answer</summary>

**B.** Project-scoped, version-controlled.

</details>

**2.** A brainstorming skill fills the main chat with long lists of alternatives. Which frontmatter option helps?

<details><summary>Answer</summary>

`context: fork` — run it in an isolated subagent; only the result comes back.

</details>

**3.** Developers often run `/fix-issue` without the issue number. What helps?

<details><summary>Answer</summary>

`argument-hint: [issue-number]` in the frontmatter, so autocomplete shows the expected argument.

</details>

**4.** "Always use uv, never pip" vs "steps to cut a release". Which goes in CLAUDE.md and which in a skill?

<details><summary>Answer</summary>

"Use uv" → CLAUDE.md (universal, always loaded). Release steps → a skill (task-specific, on demand).

</details>

**5.** You want your own stricter version of the team's `/review`. How, without affecting others?

<details><summary>Answer</summary>

A personal command/skill in `~/.claude/` with a different name, e.g. `/review-strict`.

</details>
