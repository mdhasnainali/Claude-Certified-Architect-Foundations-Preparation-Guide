# 2.1 Tool Descriptions and Boundaries

## Goal
After this you can write tool descriptions that make Claude pick the right tool, and fix misrouting at its root instead of adding layers. *(Task statement 2.1)*

## Guess first
1. Two tools: `get_customer` — "Retrieves customer information", `lookup_order` — "Retrieves order details". A user writes "check my order #12345" and the agent calls `get_customer`. What do you fix first?
2. Your system prompt says "Always analyze the content carefully." You also have a tool named `analyze_content`. Any risk?

## Idea
**The description is the main signal Claude uses to choose a tool.** On every turn Claude sees each tool's name, description and input schema — nothing else tells it which tool fits. With minimal descriptions, picks between similar tools become unreliable.

A good description (Anthropic docs: **at least 3–4 sentences**, more for complex tools) says:
- **What** the tool does and **what it returns** (and what it does *not* return).
- **When to use it — and when not**, compared with the similar tool.
- **Input formats** with example values (`#12345` or `ORD-12345`).
- **Edge cases and limits** (one record only, US stocks only, max 50 results).

**Overlap causes misrouting.** `analyze_content` and `analyze_document` with near-identical descriptions → Claude guesses. Fix both name and text: rename `analyze_content` to `extract_web_results` and say "only for web search results; never for files".

**Split a generic tool** when it hides several jobs with different outputs: `analyze_document` → `extract_data_points`, `summarize_content`, `verify_claim_against_source`, each with its own input/output contract.
**Merge tiny tools** when they do the same job on the same resource (`create_pr`, `review_pr`, `merge_pr` → one `pull_request` tool with an `action` parameter). Both moves have one aim: **less ambiguity**.

**The system prompt can override good descriptions.** Keyword-heavy instructions ("always *analyze*…") create unintended links to tools with that word in their name. When selection is wrong despite good descriptions, review the system prompt.

**Small details that matter:** unambiguous parameter names (`customer_id`, not `user`); service prefixes when tools come from many systems (`github_list_prs`, `jira_search`); return only high-signal fields.

*In Python terms:* the description is the docstring and the schema is the type hints. If two functions in a module had the same one-line docstring, a new teammate would guess too.

**Exam angle (official sample question 2):** the *first* fix for misrouting between two tools is better descriptions. Few-shot examples add tokens without fixing the cause; a keyword routing layer is over-engineering; merging the tools is valid but bigger than a "first step".

## Code

**File:** [`codes/2_1_pick_test.py`](codes/2_1_pick_test.py) · run `make run 2_1_pick_test`

Python 3.13+, `anthropic` 2.13. Needs `ANTHROPIC_API_KEY`; ~6 small calls. Save as `2_1_pick_test.py`, run `uv run --with anthropic python 2_1_pick_test.py`.

```python
# 2_1_pick_test.py — anthropic 2.13. Run: uv run --with anthropic python 2_1_pick_test.py
import anthropic

client = anthropic.Anthropic()
SOURCE_INPUT_SCHEMA = {
    "type": "object",
    "properties": {"source": {"type": "string"}},
    "required": ["source"],
}
VAGUE_TOOLS = [
    {
        "name": "analyze_content",
        "description": "Analyzes content and returns insights.",
        "input_schema": SOURCE_INPUT_SCHEMA,
    },
    {
        "name": "analyze_document",
        "description": "Analyzes a document and returns insights.",
        "input_schema": SOURCE_INPUT_SCHEMA,
    },
]
CLEAR_TOOLS = [
    {
        "name": "extract_web_results",
        "input_schema": SOURCE_INPUT_SCHEMA,
        "description": "Extract facts from WEB SEARCH RESULTS already fetched in this conversation. source = the "
        "search query they came from. Use for anything found online. Never use for files or PDFs.",
    },
    {
        "name": "analyze_document",
        "input_schema": SOURCE_INPUT_SCHEMA,
        "description": "Analyze ONE uploaded file (PDF, DOCX, report). source = file name, e.g. q3-report.pdf. "
        "Returns key figures with page numbers. Use only for files, never for web search results.",
    },
]
QUERIES = [
    "Pull the key numbers from q3-report.pdf",
    "What did the search results for 'EU AI Act fines' say?",
    "Check the report's revenue claim against what we found online",
]

def pick_tools(tools: list, query: str) -> list[str]:
    response = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=2000,
        tools=tools,
        messages=[{"role": "user", "content": query}],
    )
    return [block.name for block in response.content if block.type == "tool_use"] or [
        "(no tool)"
    ]

for query in QUERIES:
    print(
        f"{query[:40]:42} vague → {pick_tools(VAGUE_TOOLS, query)}\n"
        f"{'':42} clear → {pick_tools(CLEAR_TOOLS, query)}"
    )
```

Possible output (model picks vary between runs — that variation *is* the lesson):
```
Pull the key numbers from q3-report.pdf    vague → ['analyze_document']
                                           clear → ['analyze_document']
What did the search results for 'EU AI A   vague → ['analyze_content']
                                           clear → ['extract_web_results']
Check the report's revenue claim against   vague → ['analyze_content']
                                           clear → ['analyze_document', 'extract_web_results']
```
Strong models often guess right on easy queries. The gap shows on mixed queries and over many runs: vague picks drift, clear picks stay stable.

**Predict first, then change and run:** add `system="Always analyze the content carefully before answering."` to the `create` call and run the `VAGUE_TOOLS` set 3 times. Which tool gets picked more often?

<details><summary>Answer</summary>

Usually `analyze_content` gains picks — the keyword in the system prompt pulls Claude toward the tool with the same word in its name. That's the "keyword-sensitive instruction" trap.

</details>

## When to use · gotchas
- **Fix descriptions first** — cheapest, highest-leverage change for misrouting.
- **Describe the boundary**, not just the job: "use X for …; for … use Y instead".
- Don't paper over bad descriptions with many few-shot examples in the system prompt (token cost, root cause stays).
- **Name tools for their real scope.** A name like `analyze_content` invites everything.
- `input_examples` (API field) helps with complex or format-sensitive inputs — but descriptions come first.
- Ask a parameter for "a short explanation", not "your reasoning" (that can trigger a `reasoning_extraction` refusal on new models).

```text
get_customer — Find ONE customer account by email or customer ID (C-<n>). Returns name,
plan and identity-verification status. Use for questions about the person or the account
(login, plan, contact details, verification). Does NOT return orders — for anything about
a purchase, use lookup_order.

lookup_order — Get ONE order by order number (#12345, 12345 or ORD-12345). Returns items,
total, shipping status and ETA. Use for any question about a purchase, delivery, return or
refund status. Needs the order number, not the customer's name; if the user gives no
number, ask for it or call get_customer first.
```

## Quiz
**1.** `analyze_content` and `analyze_document` have almost the same description. Logs show web results being sent to `analyze_document`. Best fix? A) Few-shot examples in the system prompt · B) Rename `analyze_content` to `extract_web_results` and rewrite both descriptions with clear boundaries · C) A keyword router before each turn · D) Remove one tool

<details><summary>Answer</summary>

**B.** It removes the overlap at its source. A costs tokens and leaves the cause; C is over-engineering; D loses a capability.

</details>

**2.** Name four things a good tool description contains.

<details><summary>Answer</summary>

What it does and returns; when to use it and when not (vs similar tools); input formats with examples; edge cases and limits.

</details>

**3.** Descriptions are now clear, but the agent still prefers `summarize_notes` for every request. The system prompt says "Always summarize the notes you see." What is happening?

<details><summary>Answer</summary>

A keyword-sensitive instruction in the system prompt creates an unintended tool association. Reword the system prompt.

</details>

**4.** A generic `analyze_document` tool returns inconsistent output: sometimes summaries, sometimes data points. Fix?

<details><summary>Answer</summary>

Split it into purpose-specific tools with defined input/output contracts — e.g. `extract_data_points`, `summarize_content`, `verify_claim_against_source`.

</details>

**5.** Why is `customer_id` a better parameter name than `user`?

<details><summary>Answer</summary>

It is unambiguous about type and format, so Claude passes the right value. Vague names cause wrong arguments.

</details>
