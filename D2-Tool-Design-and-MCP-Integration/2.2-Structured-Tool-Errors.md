# 2.2 Structured Tool Errors

## Goal
After this you can return tool errors an agent can act on — category, retryable flag, clear message — and keep "it failed" apart from "nothing found". *(Task statement 2.2)*

## Guess first
1. A tool returns `"Operation failed"` for a timeout, for a bad order ID, and for a refund over the policy limit. What can the agent do with that?
2. An order search finds zero orders. Is that an error?

## Idea
**MCP has two error channels:**
- **Protocol errors** — a JSON-RPC `error` (unknown tool, malformed request). The model rarely recovers from these.
- **Tool execution errors** — a normal result with **`isError: true`** and a text the model reads. This is the channel for API failures, bad input and business rules, so the agent can correct itself.

In the MCP Python SDK (v2) you `raise ToolError(...)` and the result gets `isError: true`. **Never `return` an error string** — it arrives with `isError: false` and looks like a successful answer.

**Four error categories the exam names:**

| Category | Example | Retry? | What the agent should do |
|---|---|---|---|
| **transient** | timeout, 503, rate limit | yes | Retry (with backoff), ideally inside the subagent |
| **validation** | `order_id` in the wrong format | not as-is | Fix the input, then call again |
| **business** | refund over the $500 limit | no | Explain to the customer, offer the right path |
| **permission** | no access to that account | no | Stop, escalate or ask for authorisation |

A uniform `"Operation failed"` hides which case it is. The agent then retries hopeless calls (wasted turns) or gives up on recoverable ones.

**Return structured metadata** in the error text: `errorCategory`, `isRetryable`, a human-readable `message`, plus useful extras — `retry_after_s`, the attempted query, partial results, and for business errors a `customer_message` the agent can pass on politely.

**Local recovery first.** A subagent retries transient errors itself. It sends to the coordinator only what it can't fix — with what it tried and any partial results. (More in Domain 5.)

**Access failure ≠ valid empty result.**
- Database timeout → error (`isError: true`, transient, retryable).
- Query ran, no orders → **success** with an empty list (`isError: false`).
Mixing them up makes an agent tell a customer "you have no orders" while the database was down — or retry forever on a real "no match".

*In Python terms:* like raising `TimeoutError`, `ValueError` or `PermissionError` instead of a bare `except: return "failed"`. The caller's `except` blocks decide what to retry.

## Code

**File:** [`codes/2_2_errors_server.py`](codes/2_2_errors_server.py) · run `make run 2_2_errors_server`

Python 3.13+, `mcp` 2.3 (official MCP Python SDK). Offline — the client talks to the server in memory, no API key.
Save as `2_2_errors_server.py`, run `uv run --with mcp python 2_2_errors_server.py`.

```python
# 2_2_errors_server.py — mcp 2.3 (Python SDK). Offline: uv run --with mcp python 2_2_errors_server.py
import asyncio, json
from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp, gateway_calls = MCPServer("billing"), [0]

def fail(category: str, retryable: bool, message: str, **extra) -> ToolError:
    return ToolError(
        json.dumps(
            {
                "errorCategory": category,
                "isRetryable": retryable,
                "message": message,
                **extra,
            }
        )
    )

@mcp.tool()
def refund(order_id: str, amount: float) -> str:
    """Refund one order (ORD-<n>), max $500. Larger refunds need a human."""
    if not order_id.startswith("ORD-"):
        raise fail("validation", False, "order_id must look like ORD-123", got=order_id)
    if amount > 500:
        raise fail(
            "business",
            False,
            "Over the $500 agent limit.",
            customer_message="A specialist will review this refund within 24 hours.",
        )
    gateway_calls[0] += 1
    if gateway_calls[0] == 1:  # simulate one gateway timeout
        raise fail(
            "transient", True, "Payment gateway timeout after 10 s.", retry_after_s=2
        )
    return json.dumps({"refunded": amount, "order_id": order_id})

async def main():
    async with Client(mcp) as c:
        for oid, amt in [("123", 50), ("ORD-9", 900), ("ORD-9", 50), ("ORD-9", 50)]:
            r = await c.call_tool("refund", {"order_id": oid, "amount": amt})
            print(r.is_error, r.content[0].text)

asyncio.run(main())
```

Expected output (the server also logs one `Tool 'refund' failed: …` line per error to stderr):
```
True Error executing tool refund: {"errorCategory": "validation", "isRetryable": false, "message": "order_id must look like ORD-123", "got": "123"}
True Error executing tool refund: {"errorCategory": "business", "isRetryable": false, "message": "Over the $500 agent limit.", "customer_message": "A specialist will review this refund within 24 hours."}
True Error executing tool refund: {"errorCategory": "transient", "isRetryable": true, "message": "Payment gateway timeout after 10 s.", "retry_after_s": 2}
False {"refunded": 50.0, "order_id": "ORD-9"}
```
The third and fourth calls are identical. The third hit a (simulated) timeout; retrying it worked — because the error said `isRetryable: true`.

**Predict first, then change and run:** replace the `business` line with `return "Refund failed: over limit"`. What does the second line print now, and why is that dangerous?

<details><summary>Answer</summary>

`False Refund failed: over limit` — `is_error` is `False`. A client, a UI, or a hasty agent can treat it as success ("refund done"). Raise `ToolError`; the flag is the signal.

</details>

## When to use · gotchas
- **Always** set the error flag on failures; **never** on valid empty results.
- Put the category and retryability in the error — don't make the agent guess from free text.
- Business errors need a **customer-friendly** message as well as the technical one.
- Retry only what is retryable, with a limit and backoff. Retrying a validation error unchanged burns turns.
- Don't swallow errors in a subagent and return "no results" — the coordinator then makes decisions on false data.
- Protocol errors (unknown tool, malformed call) are for programming bugs, not business outcomes.

## Try it
*≤ 10 min.* Write `call_with_retry(client, name, args, tries=3)`: retry only when `isRetryable` is true, wait `retry_after_s`, and return the last result otherwise. Test it against `2_2_errors_server.py` (replace `main()`).

<details><summary>Solution</summary>

```python
async def call_with_retry(client, name: str, args: dict, tries: int = 3):
    for attempt in range(1, tries + 1):
        r = await client.call_tool(name, args)
        if not r.is_error:
            return r
        err = json.loads(r.content[0].text.split(": ", 1)[1])  # drop "Error executing tool x: "
        if not err["isRetryable"] or attempt == tries:
            return r                                          # hand the structured error upward
        print(f"attempt {attempt}: {err['errorCategory']} → retry in {err.get('retry_after_s', 1)} s")
        await asyncio.sleep(err.get("retry_after_s", 1))

async def main():
    async with Client(mcp) as c:
        print((await call_with_retry(c, "refund", {"order_id": "ORD-9", "amount": 50})).content[0].text)
        print((await call_with_retry(c, "refund", {"order_id": "ORD-9", "amount": 900})).content[0].text)
```
Output: `attempt 1: transient → retry in 2 s`, then the refund succeeds; the $900 call returns its business error at once, with no retry.

</details>

## Quiz
**1.** Every failure of your `lookup_order` tool returns `"Operation failed"`. The agent retries policy violations 5 times and gives up on timeouts. Best fix? A) Tell the agent in the prompt to retry at most twice · B) Return structured errors with `errorCategory` and `isRetryable` · C) Remove retries · D) Log errors to a file

<details><summary>Answer</summary>

**B.** Without a category and retry flag, the agent can't choose the right recovery. A and C treat all errors the same.

</details>

**2.** The customer search times out, and the tool returns `[]` with `isError: false`. What goes wrong?

<details><summary>Answer</summary>

The agent treats an access failure as a valid empty result — e.g. tells the customer they have no account. Return a transient error with `isError: true` instead.

</details>

**3.** A refund is refused because it breaks a policy. Which two fields help the agent talk to the customer well?

<details><summary>Answer</summary>

`isRetryable: false` (stop trying) and a customer-friendly message explaining the next step (e.g. human review within 24 h).

</details>

**4.** Fix the bug: an MCP tool built with the Python SDK does `return f"Error: {e}"` in its `except` block.

<details><summary>Answer</summary>

Returned strings carry `isError: false` and look like success. `raise ToolError(...)` with structured details instead.

</details>

**5.** A search subagent hits a timeout. What should it do before telling the coordinator?

<details><summary>Answer</summary>

Retry locally (it's transient). Only if that fails, propagate a structured error with what it attempted and any partial results.

</details>
