# 5.1 Case Facts and Long Context

## Goal
After this you can keep exact facts alive through a long conversation: a case-facts block, trimmed tool outputs, and a layout that beats "lost in the middle". *(Task statement 5.1)*

## Guess first
1. After 40 turns, the running summary says "customer wants a refund soon". The customer actually said "$650 back to my original card by 27 Nov". What did summarising lose?
2. You put 12 search results into one prompt. Which ones is Claude most likely to under-use?

## Idea
The API is stateless: every request must carry the conversation history, or Claude loses the thread. Long chats get summarised to fit — and **progressive summarisation blurs exact values**: amounts, percentages, dates, order numbers, and what the customer said they expect become "a refund soon".

**Fix 1 — a case-facts block.** Pull transactional facts (IDs, amounts, dates, statuses, customer expectations) into a structured block. Put it in **every** prompt, **outside** the summarised history, and update it with code when facts change. With several issues in one chat, keep one entry per issue.

**Fix 2 — trim tool outputs before they pile up.** An order lookup that returns 40+ fields when 5 matter eats context on every later turn. Keep only the relevant fields before the result enters the history (in your tool wrapper, or a `PostToolUse` hook — see [1.5 Hooks](../D1-Agentic-Architecture-and-Orchestration/1.5-Hooks.md)).

**Fix 3 — position-aware layout.** Models use the **start** and **end** of a long input reliably and may skip findings in the **middle** ("lost in the middle"). So:
- put a short **key-findings summary first**, then the details under clear section headers;
- put long documents near the top and the question/task **at the end** (Anthropic: queries at the end can improve quality by up to 30% on complex multi-document inputs);
- wrap each document in tags with its metadata (`<document><source>…</source><document_content>…</document_content></document>`).

**Fix 4 — lean hand-offs.** When a downstream agent has a small context budget, upstream agents should return **structured data** (key facts, citations, relevance scores, dates, where each fact came from) — not long prose and reasoning chains.

*In Python terms:* the case-facts block is like keeping state in a dict you update, instead of re-reading a chat log that someone keeps rewriting shorter.

```python
# 5_1_case_context.py — Python 3.13+, offline. Build every turn's prompt so key facts can't get lost.
import json

ORDER = {
    "order_id": "ORD-9",
    "status": "delivered",
    "total": 650.0,
    "delivered_at": "2026-11-20",
    "return_window_days": 30,
    **{f"internal_field_{i}": "x" * 20 for i in range(40)},
}
KEEP = ("order_id", "status", "total", "delivered_at", "return_window_days")

def trim(record: dict) -> dict:  # cut tool output BEFORE it enters the history
    return {k: record[k] for k in KEEP if k in record}

CASE_FACTS = {  # exact values, kept OUTSIDE the summarised history
    "customer_id": "C7",
    "verified": True,
    "issues": [
        {
            "order_id": "ORD-9",
            "problem": "arrived broken",
            "amount": 650.00,
            "status": "refund awaiting approval",
        },
        {
            "order_id": "ORD-12",
            "problem": "charged twice",
            "amount": 89.99,
            "status": "investigating",
        },
    ],
    "customer_expects": "refund to original card by 2026-11-27",
}

def build_prompt(summary: str, recent: list[str], question: str) -> str:
    return (
        f"<case_facts>\n{json.dumps(CASE_FACTS)}\n</case_facts>\n"  # top: always present, exact
        f"<earlier_conversation_summary>\n{summary}\n</earlier_conversation_summary>\n"
        f"<recent_turns>\n" + "\n".join(recent) + "\n</recent_turns>\n"
        f"<task>\n{question}\n</task>"
    )  # bottom: the ask

print(
    "order record:",
    len(json.dumps(ORDER)),
    "chars → trimmed:",
    len(json.dumps(trim(ORDER))),
    "chars",
)
print(
    build_prompt(
        "Customer reported two problems; identity verified; damage photo received.",
        ["Customer: Any news on the double charge?"],
        "Write the next reply to the customer.",
    )
)
```

The trimmed record is ~16× smaller. The summary can be vague — the exact numbers still reach Claude every turn.

**Predict first, then check:** imagine the case facts were only written in turn 3 and later folded into the summary. After 30 turns, which values are most at risk?

<details><summary>Answer</summary>

The precise ones: `89.99`, `650.00`, the date `2026-11-27`, "original card", and which problem belongs to which order. Summaries keep the gist and drop exact values — the reason the block lives outside the summary.

</details>

## When to use · gotchas
- Always send the **full** history the model needs (or history summary **plus** case facts). Dropping turns breaks coherence.
- Update case facts **in code** from tool results, not by asking the model to remember.
- Trim **before** appending a tool result. Afterwards it is already in every future request.
- Don't bury the key result in the middle of 20 pages. Lead with a summary; use headers.
- Exam distractor: "use a model with a bigger context window" — more room doesn't fix blurred summaries or position effects.

## Try it
*≤ 10 min.* Write `update_issue(order_id, **changes)` that updates one issue in `CASE_FACTS` (e.g. status → `"refunded"`, plus `refund_date`). Call it, then rebuild the prompt.

<details><summary>Solution</summary>

```python
def update_issue(order_id: str, **changes) -> None:
    for issue in CASE_FACTS["issues"]:
        if issue["order_id"] == order_id:
            issue.update(changes)
            return
    raise KeyError(f"no issue for {order_id}")

update_issue("ORD-12", status="refunded", refund_date="2026-11-24")
print(build_prompt("…", ["Customer: thanks!"], "Close the case politely."))
```

</details>

## Quiz
**1.** In long support chats the agent starts quoting wrong refund amounts. History is summarised every 10 turns. Best fix? A) Summarise less often · B) A persistent case-facts block with exact amounts, dates and order IDs in every prompt, outside the summary · C) A bigger context window · D) Ask the agent to double-check numbers

<details><summary>Answer</summary>

**B.** Summaries blur exact values; a structured block keeps them exact every turn.

</details>

**2.** Each order lookup returns 45 fields; only 5 matter for returns. After many lookups, quality drops. Fix?

<details><summary>Answer</summary>

Trim tool outputs to the relevant fields before they enter the conversation history.

</details>

**3.** A synthesis prompt holds 15 findings. The report often misses findings 6–10. Why, and what helps?

<details><summary>Answer</summary>

"Lost in the middle": the start and end are used most reliably. Put a key-findings summary at the beginning, organise details under explicit headers, and keep the task at the end.

</details>

**4.** A downstream agent with a small context budget gets 20k tokens of upstream reasoning. Better design?

<details><summary>Answer</summary>

Have the upstream agent return structured data — key facts, citations, relevance scores — instead of verbose content and reasoning.

</details>

**5.** Why must each API request include the conversation history?

<details><summary>Answer</summary>

The API is stateless. Without the history (or a faithful summary plus case facts), Claude loses what was said and done.

</details>
