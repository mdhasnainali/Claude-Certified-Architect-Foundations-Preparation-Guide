# 5.3 Error Propagation

## Goal
After this you can pass failures up a multi-agent system so the coordinator can recover — without hiding them and without crashing the whole run. *(Task statement 5.3)*

## Guess first
1. The web search subagent times out. Is returning `results: []` with "success" a safe choice?
2. One of five research subagents fails. Should the whole report stop?

## Idea
[2.2 Structured Tool Errors](../D2-Tool-Design-and-MCP-Integration/2.2-Structured-Tool-Errors.md) was about one **tool** reporting an error. This lesson is one level up: a **subagent** reporting to the **coordinator**.

**Send structured error context:**
- **failure type** (timeout, access denied, source missing),
- **what was attempted** (the query, how many retries),
- **partial results** it already has,
- **alternative approaches** it can suggest.

With that, the coordinator can choose: retry with a changed query, try another source, or go on with partial results and mark the gap. (Official sample question 8, answer A.)

**Three anti-patterns:**
| Anti-pattern | Why it is wrong |
|---|---|
| Generic status: `"search unavailable"` | Hides what failed and what was tried; the coordinator can't decide |
| **Silent suppression**: empty result marked as success | The report states a false "no data" — worst case, nobody notices |
| **Kill everything** on one failure | Throws away good work when recovery was possible |

**Access failure ≠ valid empty result.**
- Timeout / no access → the query did **not** run; needs a retry decision.
- Query ran, nothing matched → a **real** finding ("no sources found").
Report them differently, so the coordinator doesn't retry a real "nothing" or trust a fake one.

**Recover locally first.** A subagent retries transient errors itself (with a limit). It escalates only what it can't fix, with what it tried and any partial results.

**Show coverage in the output.** The final synthesis says which areas are well supported and which have **gaps because sources were unavailable**. Readers can then judge the report honestly.

*In Python terms:* `raise SearchTimeout(query=q, partial=rows) from e` — not `except: return []` (silent) and not `sys.exit(1)` (kill all).

## Code

**File:** [`codes/5_3_propagate.py`](codes/5_3_propagate.py) · run `make run 5_3_propagate`

Python 3.13+, offline, no API key. Save as `5_3_propagate.py`, run `python3 5_3_propagate.py`.

```python
# 5_3_propagate.py — Python 3.13+, offline. Subagents report failures as data; the coordinator decides.
import json

def search_subagent(subtopic: str) -> dict:
    if subtopic == "music":  # timed out twice, kept what it had
        return {
            "status": "partial",
            "failure_type": "timeout",
            "attempted": "'AI music royalties 2025-2026', 2 retries",
            "partial_results": [
                {
                    "claim": "AI-made tracks on streaming tripled",
                    "source": "https://example.org/a",
                }
            ],
            "alternatives": ["search trade-press archive", "narrow to 2026"],
        }
    if subtopic == "film":  # search worked, nothing relevant exists
        return {"status": "ok", "results": []}
    return {
        "status": "ok",
        "results": [
            {
                "claim": f"AI tools are common in {subtopic}",
                "source": "https://example.org/b",
            }
        ],
    }

findings, coverage = [], {}
for subtopic in ("visual art", "music", "film"):
    report = search_subagent(subtopic)
    if report["status"] == "partial":  # failure WITH context → recover, don't crash
        findings += report["partial_results"]
        coverage[subtopic] = (
            f"PARTIAL ({report['failure_type']}; tried {report['attempted']}). "
            f"Next: {report['alternatives'][0]}"
        )
    elif not report["results"]:  # valid empty result → a real gap, not an error
        coverage[subtopic] = "GAP: searched successfully, no sources found"
    else:
        findings += report["results"]
        coverage[subtopic] = "covered"

print(json.dumps(coverage, indent=1))
print(len(findings), "findings kept for synthesis")
```

Expected output:
```
{
 "visual art": "covered",
 "music": "PARTIAL (timeout; tried 'AI music royalties 2025-2026', 2 retries). Next: search trade-press archive",
 "film": "GAP: searched successfully, no sources found"
}
2 findings kept for synthesis
```

**Predict first, then change and run:** make the music subagent "handle" its timeout silently: `return {"status": "ok", "results": []}`. What does the coverage line for music say now, and why is that dangerous?

<details><summary>Answer</summary>

`"GAP: searched successfully, no sources found"` — a false statement. The search never ran properly, the partial finding is lost, and the report tells readers that no sources exist. That is silent suppression.

</details>

## When to use · gotchas
- Every failure report needs: what failed, what was tried, what was found anyway.
- Retry with **changed** input (narrower query, other source) — not the same call again and again.
- Partial results are valuable; never drop them because "the step failed".
- Put coverage notes in the final report, not only in logs.
- Exam distractor: "retry with exponential backoff, then return 'search unavailable'". Retry is fine; the generic message at the end is the problem.

## Try it
*≤ 10 min.* Add coordinator recovery: when a subagent returns `partial`, call `search_subagent` once more with the first alternative (pretend that alternative works) and merge the results. Update the coverage line to say it was recovered.

<details><summary>Solution</summary>

```python
def retry_with(alternative: str) -> dict:   # stand-in for re-delegating with a changed query
    return {"status": "ok", "results": [{"claim": "Royalty payouts fell 9%", "source": "trade-press archive"}]}

for subtopic in ("visual art", "music", "film"):
    report = search_subagent(subtopic)
    if report["status"] == "partial":
        retry_report = retry_with(report["alternatives"][0])
        findings += report["partial_results"] + retry_report["results"]
        coverage[subtopic] = f"RECOVERED via '{report['alternatives'][0]}' after {report['failure_type']}"
    # ... other branches unchanged
```

</details>

## Quiz
**1.** The web search subagent times out on a complex topic. Which design lets the coordinator recover best? A) Structured context: failure type, attempted query, partial results, alternatives · B) Retry with backoff, then return "search unavailable" · C) Catch the timeout, return empty results marked successful · D) Raise to a top-level handler that ends the workflow

<details><summary>Answer</summary>

**A.** B hides context, C suppresses the error, D throws away recoverable work.

</details>

**2.** Why is "empty result marked as success" worse than a crash?

<details><summary>Answer</summary>

A crash is visible. Silent suppression produces a confident report with false gaps or false conclusions that nobody questions.

</details>

**3.** A subagent got a timeout once, retried, and succeeded. Should it report the timeout to the coordinator?

<details><summary>Answer</summary>

Not as an error — it recovered locally. It may log it. Only unresolved failures go up, with context.

</details>

**4.** The final report shows no sign that the music sources were unreachable. What output feature is missing?

<details><summary>Answer</summary>

Coverage annotations: which findings are well supported, and which areas have gaps because sources were unavailable.

</details>

**5.** A database query returns no rows. A different call times out. How should the subagent report each?

<details><summary>Answer</summary>

No rows → success with an empty result (a real finding). Timeout → structured error (access failure) so the coordinator can decide on a retry.

</details>
