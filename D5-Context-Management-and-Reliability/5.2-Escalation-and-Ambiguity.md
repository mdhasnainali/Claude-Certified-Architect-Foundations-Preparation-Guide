# 5.2 Escalation and Ambiguity

## Goal
After this you can make an agent escalate the right cases — not the easy ones, not too late — and ask instead of guessing when data is ambiguous. *(Task statement 5.2)*

## Guess first
1. A customer is very angry, but the problem is a simple damaged item with a photo. Escalate?
2. A lookup returns three customers named "John Smith". Should the agent pick the one with the most recent order?

## Idea
**Good escalation triggers:**
1. **The customer asks for a human** → escalate **at once**. No "let me look into it first".
2. **Policy exception or gap** → the policy is silent or unclear on this request. Example: the customer wants you to match a *competitor's* price, but the policy only covers your own price changes.
3. **No meaningful progress** → the agent can't move the case forward.

**Bad triggers (exam traps):**
- **Sentiment / frustration alone.** Anger doesn't mean complexity.
- **"The case is complex"** on its own.
- **Self-reported confidence scores** ("rate 1–10, escalate below 6"). LLM self-confidence is poorly calibrated — the agent is often confidently wrong on the hard cases.

**Frustrated but simple:** acknowledge the frustration, offer the fix. Escalate only if the customer **repeats** that they want a person.

**How to fix bad calibration** (official sample question 3): put **explicit escalation criteria with few-shot examples** in the system prompt. That is the proportionate first step — before sentiment analysis or a separate classifier model.

**Ambiguous data → ask, don't guess.** When a tool returns several matches, ask for another identifier (email, order number, postcode). Picking by a heuristic ("most recent", "first in the list") risks refunding the wrong person.

**Measure it.** Anthropic's support guide suggests tracking escalation accuracy — correctly escalated cases vs. ones that should have been escalated but weren't (aim ≥ 95%) — next to deflection rate (typically 70–80% handled without a human).

*In Python terms:* like Django's `Model.objects.get()` raising `MultipleObjectsReturned` instead of quietly returning the first row.

## Code

**File:** [`codes/5_2_escalate_test.py`](codes/5_2_escalate_test.py) · run `make run 5_2_escalate_test`

Python 3.13+, `anthropic` 2.13. Needs `ANTHROPIC_API_KEY`; 4 small calls. Save as `5_2_escalate_test.py`, run `uv run --with anthropic python 5_2_escalate_test.py`.

```python
# 5_2_escalate_test.py — anthropic 2.13. Run: uv run --with anthropic python 5_2_escalate_test.py
import anthropic

client = anthropic.Anthropic()
SYSTEM_PROMPT = """You are a support agent for an online shop.
Call escalate_to_human when: the customer asks for a person (at once, no investigation first);
policy is silent or unclear on the request; or you cannot make progress.
Do NOT escalate only because the customer is upset or the case has several steps.
If a lookup returns several matching customers, call ask_customer for another identifier.
Otherwise call resolve.
<example>"Third broken mug!! Fix it." → resolve: damage replacement; acknowledge the frustration.</example>
<example>"Amazon is $20 cheaper, match it." → escalate_to_human: policy covers only our own price changes.</example>"""

def make_tool(name: str, description: str) -> dict:
    return {
        "name": name,
        "description": description,
        "input_schema": {
            "type": "object",
            "properties": {"note": {"type": "string"}},
            "required": ["note"],
        },
    }

TOOLS = [
    make_tool("escalate_to_human", "Hand the case to a human. note = reason."),
    make_tool(
        "ask_customer", "Ask the customer ONE clarifying question. note = the question."
    ),
    make_tool("resolve", "Solve the case within policy. note = the action taken."),
]
CUSTOMER_MESSAGES = [
    "I want to talk to a real person, now.",
    "My parcel came damaged, photo attached. So annoying!!",
    "Can you match the price BestDeals has for this TV?",
    "Refund my order. I'm John Smith. [lookup: 3 customers named John Smith]",
]

for customer_message in CUSTOMER_MESSAGES:
    response = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=2000,
        system=SYSTEM_PROMPT,
        tools=TOOLS,
        messages=[{"role": "user", "content": customer_message}],
    )
    tools_called = [
        block.name for block in response.content if block.type == "tool_use"
    ]
    print(f"{customer_message[:46]:48} → {tools_called or ['(text only)']}")
```

Expected output (a run can differ on borderline wording):
```
I want to talk to a real person, now.            → ['escalate_to_human']
My parcel came damaged, photo attached. So ann   → ['resolve']
Can you match the price BestDeals has for this   → ['escalate_to_human']
Refund my order. I'm John Smith. [lookup: 3 cu   → ['ask_customer']
```

**Predict first, then change and run:** delete the line "Do NOT escalate only because the customer is upset…" and the first `<example>`. Run it 3 times. What changes for case 2?

<details><summary>Answer</summary>

Case 2 escalates more often: without the boundary and the example, "So annoying!!" reads as a reason to hand over. Explicit criteria + examples are what keep easy-but-emotional cases with the agent.

</details>

## When to use · gotchas
- An explicit request for a human beats everything — even when the agent could solve it.
- Write criteria as **conditions** ("policy silent on X"), not feelings ("if the customer seems unhappy").
- Few-shot examples should show the **borderline** cases (angry + simple, polite + policy gap), with the reason.
- Never pick between multiple matches by heuristic. Ask.
- When you escalate, send the structured handoff from [1.4 Enforcement and Handoffs](../D1-Agentic-Architecture-and-Orchestration/1.4-Enforcement-and-Handoffs.md).

## Quiz
**1.** The agent resolves only 55% of contacts (target 80%). Logs: it escalates easy damage cases with photos but tries to handle policy exceptions itself. Best first fix? A) Self-reported confidence with a threshold · B) Explicit escalation criteria with few-shot examples in the system prompt · C) A classifier trained on old tickets · D) Escalate on negative sentiment

<details><summary>Answer</summary>

**B.** It fixes the unclear decision boundary directly. A is badly calibrated, C is over-engineered for a first step, D measures the wrong thing.

</details>

**2.** A customer writes "Get me a human." The issue looks easy. What does the agent do?

<details><summary>Answer</summary>

Escalate immediately — honour the explicit request without investigating first.

</details>

**3.** A customer asks for a price match with a competitor. Policy only mentions adjustments for the shop's own price drops. Escalate?

<details><summary>Answer</summary>

Yes — the policy is silent on this request (a policy gap), so a human should decide.

</details>

**4.** `get_customer` returns 2 accounts for "Ana Lee". The agent picks the one with the latest order. What's wrong, and what should it do?

<details><summary>Answer</summary>

Heuristic selection can act on the wrong account. Ask the customer for another identifier (email, order number).

</details>

**5.** Why are self-reported confidence scores a poor escalation trigger?

<details><summary>Answer</summary>

LLM self-confidence is poorly calibrated: the agent is often confident on exactly the hard cases it gets wrong. Explicit criteria work better.

</details>
